# 문장 → 색감 고도화 (42 · 43 · 44단계) — 설계

2026-10-02 대표와 합의. BM25 검증 실험을 끝내고 "자연어로 말하면 색감을 뽑아 주는 앱" 쪽으로 간다.

## 1. 무엇이 안 되나 · 왜 문제인가

지금 추천 경로는 문장을 받아 **미리 적어 둔 배색 16쌍 중 하나를 검색으로 고르고**, 그 두 색을 배색 구조로 불린다.
그래서:

| 증상 | 쉽게 말하면 |
|---|---|
| 결과가 단조롭다 | 어떤 문장을 넣어도 16쌍 중 하나에서 출발한다 |
| 뉘앙스가 안 먹는다 | "차분한데 포인트는 강렬하게" 처럼 조건이 둘이면 담을 그릇이 없다 — 검색은 문서 하나를 고를 뿐이다 |
| 대화로 다듬을 수 없다 | "좀 더 따뜻하게" 는 새 검색이 되어 앞의 결과와 이어지지 않는다 |
| 쓰임새·색 개수를 못 정한다 | "UI 용 5색" 을 말해도 늘 2색 쌍 + 구조 3~4색이다 |

이 구조는 "BM25 + 질의 재작성이면 충분하다" 는 주장을 시험하려고 **일부러** 그렇게 만든 것이다. 실험을 끝내면 그 제약을
풀 수 있다.

## 2. 합의한 방향 (대표 답, 2026-10-02)

| 질문 | 답 |
|---|---|
| 문장 → 색은 어떻게 | **Claude 는 의도만 읽고 색은 엔진이 계산한다** |
| 검색 장치(BM25 · 로컬 Ollama 임베딩) | **걷어낸다** |
| 아쉬운 점 | 단조로움 · 뉘앙스 · 대화로 다듬기 · 쓰임새/색 개수 — **넷 다** |
| 진단 · 캐릭터 · 색 코드 경로 | **그대로 두고 추천만 고도화** |
| 한 번에 보여 줄 안 | **3안** |
| 순서 | **42 → 43 → 44** |

버린 대안:
- **Claude 가 헥스까지 직접** — 가장 빨리 좋아지지만 같은 문장이 매번 다른 색을 내 게이트로 품질을 못 지킨다. 이 저장소가 지켜
  온 "헥스를 지어내지 않는다" 와도 부딪힌다.
- **검색은 두고 코퍼스를 수백 건으로** — 출처 있는 색만 나오지만 일의 대부분이 데이터 수집이 되고, 뉘앙스·다듬기는 여전히 안 된다.

## 3. 흐름

```
"비 오는 날 서점, 차분한데 포인트는 주황"
   → Claude(src/intent.js): 의도 JSON — 아래 표의 칸만 채운다. 헥스 칸이 스키마에 없다
   → 검증(src/compose.js parseIntent): 모르는 값·범위 밖은 버리거나 기본값
   → 엔진(src/compose.js compose): 의도 → 색. 같은 의도 = 늘 같은 색
   → 화면: 3안(충실 · 부드럽게 · 대담하게) + "이렇게 읽었어요" 한 줄 + 읽은 칸들
```

### 3.1 의도의 칸

| 칸 | 쉽게 말하면 | 값 |
|---|---|---|
| `kind` | 색을 찾는 말인가 | `palette` · `diagnosis`(배색 고칠 곳을 말함) · `other`(색과 무관) |
| `usage` | 어디에 쓰나 | `general` · `ui` · `illustration` · `brand` |
| `count` | 몇 색 | 3~7 정수, 말 안 하면 5 |
| `base.hues` | 주로 무슨 색 | 색상 낱말 1~3개 |
| `base.tone` | 주로 얼마나 밝고 탁한가 | PCCS 12톤 중 하나 |
| `accent` | 따로 튀는 색 하나 | `{hue, tone}` 또는 없음 |
| `temperature` | 따뜻/차가움 | `warm` · `cool` · `neutral` |
| `contrast` | 명도 차이를 얼마나 | `low` · `medium` · `high` |
| `avoid` | 빼 달라는 색 | 색상 낱말 0~3개 |
| `reading` | 어떻게 읽었는지 한 줄 | 한국어 80자 이하. **화면에 그대로 나간다** — 사용자가 "왜 이 색이지" 를 답할 수 있게 |

색상 낱말 13개: `red` `orange` `yellow` `yellow-green` `green` `teal` `cyan` `blue` `indigo` `purple` `magenta` `pink` `neutral`.
갈색은 따로 없다 — "주황 + 어두운/탁한 톤" 으로 읽게 프롬프트가 안내한다(PCCS 도 갈색을 톤으로 다룬다).

톤 12개(PCCS): `vivid` 선명한 · `strong` 강한 · `bright` 밝은 · `light` 연한 · `pale` 아주 연한 · `soft` 부드러운 ·
`dull` 탁한 · `deep` 짙은 · `dark` 어두운 · `light-grayish` 밝은 회색빛 · `grayish` 회색빛 · `dark-grayish` 어두운 회색빛.

### 3.2 엔진 — 의도 → 색

**색 좌표는 OKLCH 다.** 사람이 느끼는 밝기(L)·선명함(C)·색상각(h)을 따로 움직일 수 있는 좌표다. 지금 쓰는 HSL 은
"같은 L" 이어도 노랑이 파랑보다 훨씬 밝아 보여, "같은 톤의 다른 색" 을 만들면 톤이 깨진다. 미뤄 둔 B1(OKLCH)이 이것이다.

- **톤 → (L, 상대 채도).** 상대 채도는 "그 밝기·그 색상에서 화면이 낼 수 있는 가장 선명한 정도" 의 몇 %인가다. 그래야
  "선명한 노랑" 과 "선명한 파랑" 이 둘 다 제 색의 끝까지 간다. 톤별 수치는 **`[판단]`** — 원전(PCCS)은 톤을 이름과 그림으로
  주고 OKLCH 수치는 안 준다. `src/compose.js` 한 곳에 둔다.
- **색상 낱말 → 색상각.** OKLCH 색상각 대표값 `[판단]`. 같은 파일.
- **화면 밖 색 처리.** sRGB 로 못 내는 색은 L·h 를 지키고 C 만 줄인다(이진 탐색).
- **배치.** 바탕 색상들에 `count − (포인트 있으면 1)` 칸을 나눠 주고, 대비 칸이 정한 폭으로 명도를 벌린다(약 0.12 · 중 0.25 · 강 0.45 `[판단]`).
  포인트는 마지막 칸 하나. **포인트가 있으면 그 색이 가장 선명해야 한다** — 원전 color-design 의 "강조색은 나머지를 눌러야
  산다" 를 엔진이 보장한다(포인트보다 선명한 바탕색은 눌러 내린다).
- **뺄 색.** 어느 칸도 뺄 색상각 ±20° 안에서 C 0.04 를 넘지 않는다. 바탕·포인트에 뺄 색이 오면 검증 단계에서 버린다.
- **온도.** `neutral` 색상의 기운(따뜻 → 70°, 차가움 → 250°, 아주 옅게)을 정하고, 3안 중 대담안의 색상 흔들기 방향을 정한다.
- **UI 쓰임새.** 역할이 바탕 · 면 · 본문 · 주색 · 강조 순으로 붙고(색 개수만큼), **본문 대 바탕 4.5:1 · 주색/강조 대 바탕 3:1**
  (WCAG 1.4.3 · 1.4.11 `[문헌]`)을 엔진이 보장한다 — 모자라면 L 을 바탕 반대쪽으로 민다. **UI 에서 "포인트가 가장 선명" 은
  바탕 · 면 · 테두리 · 본문에만 건다** — 주색 · 보조는 강조와 나란히 서는 부품 색이라, 누르면 "강한 파랑" 이 청록 포인트 아래로
  끌려 탁해졌다(#516C95, 실측 10-02).
- **그 밖의 쓰임새.** 역할은 주조색 · 보조색 · 보조색 2 … · 강조색. 기본 면적은 주조색이 가장 크고 강조색이 10 `[판단]`.

### 3.3 3안

같은 의도에서 결정적으로 셋을 낸다. 난수 없음.

| 안 | 쉽게 말하면 | 무엇을 바꾸나 `[판단]` |
|---|---|---|
| 충실 | 읽은 그대로 | 그대로 |
| 부드럽게 | 한 톤 차분하게 | 상대 채도 × 0.7 · 명도 폭 × 0.75 |
| 대담하게 | 한 톤 세게 | 상대 채도 × 1.2(상한 1) · 명도 폭 × 1.3 · 바탕 색상 간격 +15° · 포인트 최대 채도 |

### 3.4 Claude 를 못 쓸 때

42·43단계 동안은 **옛 검색 경로로 물러선다**(키 없음 · 크레딧 소진 · 시간 초과 · 거절). 옛 게이트 276개와 오프라인 동작을
44단계까지 그대로 지키기 위한 **과도기 장치**다. 44단계에서 검색을 걷어내면 "문장을 못 읽었다 — 색 코드로 찾아 보세요" 로
바뀐다(지어내지 않는다).

`kind: diagnosis` 면 옛 검색 경로(진단을 찾는 길)로 넘긴다 — 44단계에서 "Claude 가 진단 18건 중 고르기" 로 바뀐다.
`kind: other` 면 지금처럼 되묻는다.

**라우터가 진단이라고 해도 Claude 에게 한 번 묻는다**(구현 중 추가, 10-02 실측). 진단 별칭은 BM25 시절 검색용 낱말이라 팔레트 문장에도
걸린다("차분한데 포인트는 주황" → '차분하게 하고 싶다'). Claude 가 팔레트로 읽으면 팔레트로, 진단 · 무관으로 읽으면 옛 진단 검색으로.
**"포인트" · "강조" 만 있고 다른 부위가 없으면 캐릭터 부위로 안 센다** — "포인트는 주황" 이 캐릭터로 갔다.
자세한 기록: `docs/troubleshootings/2026-10-02-palette-sentence-misrouted.md`

### 3.5 저장

**색이 아니라 의도와 안 번호를 저장한다.** 서버가 같은 검증(`parseIntent`)을 거쳐 다시 계산한다 — "화면이 준 색을 안 믿는다"
(S4 · S18)와 같은 규칙이다. 항목은 `kind: "derived"` · `structureId: "generated"` 라 `/saved` · 비율 재조정 · 메모 · 엔진
내보내기가 캐릭터 저장(34단계)과 같은 길로 돈다. 같은 의도 · 같은 안이면 덮어쓰고 비율 · 메모 · 재질을 이어받는다.

## 4. 단계

| 단계 | 무엇 | 쉽게 말하면 |
|---|---|---|
| **42** | 의도 → 색 엔진 · 추천 경로 교체 · 3안 · 쓰임새 · 색 개수 · 저장 | 새 방식으로 색이 나온다 |
| **43** | 대화로 다듬기 | 다음 말이 오면 Claude 가 **직전 의도를 고친다.** 화면에 "따뜻함 ↑ · 파랑 뺌" 처럼 무엇이 바뀌었는지 |
| **44** | 검색 장치 걷어내기 | 진단: 라우터가 이미 잡은 진단 id → 못 잡으면 Claude 가 18건 중 고르기. 캐릭터: 이미 부르는 Claude 호출에 "16쌍 중 어울리는 쌍" 칸. BM25 · 임베딩 · Ollama 코드와 그 게이트 은퇴. Ollama 를 안 띄워도 되고 배포 문제(I4)가 같이 사라진다 |

검색 제거를 마지막에 두는 이유: 42 · 43 동안 진단 · 캐릭터가 그대로 돌아서 한 번에 한 곳만 바뀐다.

## 5. 42단계 게이트 (먼저 쓰고 일부러 망가뜨려 확인한다)

| 게이트 | 지키는 것 |
|---|---|
| 결정성 | 같은 의도 → 같은 헥스(3안 모두) |
| 색을 안 지어냄 | 의도 스키마에 헥스 칸이 없고, 모델 답에 헥스를 섞어 보내도 결과가 안 바뀐다 |
| 검증 | 모르는 색상 낱말 · 톤 · 범위 밖 개수 · 타입 위장(`["ui"]`) · `__proto__` 를 버린다 |
| 개수 | 결과 색 수 = `count` (3~7) |
| 뺄 색 | 어느 칸도 뺄 색상각 ±20° 에서 C 0.04 를 안 넘는다 |
| 포인트 | 포인트가 있으면 가장 선명하다(UI 는 바탕 · 면 · 테두리 · 본문보다) |
| UI 대비 | 본문/바탕 ≥ 4.5 · 주색·강조/바탕 ≥ 3 — 의도 전 조합(색상 13 × 톤 12 × 대비 3)에서 |
| 화면 안 | 모든 색이 sRGB 안(왕복 오차 없음) |
| 3안이 다르다 | 세 안이 서로 다른 헥스를 낸다 |
| 경로 | `/api/chat` 추천 경로가 의도를 부르고 `generated` 를 낸다 · Claude 실패면 옛 검색으로 · `diagnosis` 면 옛 검색으로 · `other` 면 되묻는다 |
| 저장 | 의도 · 안 번호로만 저장되고 서버가 다시 계산한다 · 거짓 색은 무시 · 덮어쓰기와 이어받기 |
| 사용자 문장 자리 | 사용자 문장은 user 자리에만 간다 |
