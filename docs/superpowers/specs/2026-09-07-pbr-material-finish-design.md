## 1. 맥락 — 무엇이 문제인가

요청은 이렇게 들어왔다.

> "네온 사인 빛의 어두운 사이버펑크 풍의 색감" 이라고 넣었을 때 색감이 나오게 하고 싶은데,
> 이를 위해 이미션·메탈릭 등의 감촉도 표현할 수 있도록 구현하고 싶다.

### 검색은 이미 맞게 걸린다 `[실측]`

그 질의를 현재 코드에 그대로 넣으면 **LLM 을 부르지 않고 1단계에서 정확히 걸린다.**

```
질의: "네온 사인 빛의 어두운 사이버펑크 풍의 색감"
→ stage 1, route "palette", confident=true
   pair-06  자홍 #B73F74 × 진파랑 #005B8D
   matched: 네온(2.6589, whole) · 사이버펑크(2.3107, whole)   wholeMatches=2
   tags: 밤 · 네온 · 도시 · 퇴폐 · 디스토피아 · 사이버펑크 · 야경 · 클럽
   impression: "어둠 속에서 인공조명을 받고 있는 상태를 전제한다"
```

**그러므로 이 작업은 검색·RAG 문제가 아니다.** 코퍼스에 이미 정답이 있고 BM25 가 찾아낸다.

### 그런데 산출물이 평평한 색칩 두 장이다

자홍과 진파랑을 50:50 사각형으로 늘어놓으면 사이버펑크가 아니라 그냥 두 색이다.
네온으로 읽히게 만드는 것은 헥스가 아니라 **어두운 바탕 · 좁은 면적 · 번지는 빛**이고,
지금 산출물(`헥스 + 면적 %`)에는 그 셋을 담을 자리가 없다.

### 게임 엔진이면 이야기가 더 구체적이다

산출물을 유니티·언리얼에서 쓴다는 것이 확인되면서 요구가 정확해졌다.
PBR 에서 **메탈릭과 러프니스는 헥스가 아니라 0~1 스칼라**이고, **이미션은 헥스 + 세기**다.
헥스 하나로 표현되는 것은 Base Color 뿐이다.

## 2. 합의된 결정 네 가지

| 물은 것 | 고른 것 |
|---|---|
| 산출물의 형태 | **머티리얼 파라미터 한 벌** (헥스 + 스칼라) |
| 재질이 붙는 단위 | **역할마다 머티리얼 하나** — 배색 한 장 = 머티리얼 3~4벌 |
| 엔진 차이 처리 | **내부 표현 한 벌 + 엔진별 변환** (Unity 탭 / Unreal 탭) |
| 이번 단계의 범위 | **순수 엔진만.** 화면·API·LLM 없음 |

역할 이름은 `expand.js` 가 정하고 구조마다 다르다 — 대부분 `바탕 · 본문 · 강조` 셋이고,
`명도 스케일` 은 `면` 이 하나 더 붙어 넷, `공기원근` 은 `먼 쪽 · 중간 · 가까운 쪽` 이다.
재질 배정은 이 이름들을 그대로 받는다.

두 번째가 중요하다. "네온 사인 빛의 어두운 사이버펑크"는 재질 하나가 아니라 **씬**이다 —
어두운 무광 콘크리트 바탕, 젖은 금속 표면, 발광하는 사인. 파생 결과가 이미 들고 있는
`바탕 / 본문 / 강조` 역할과 그대로 겹친다. 배색 한 장에 재질 하나만 입히면
**"어둠 속 네온"을 만들 수 없다** — 발광은 주변이 어두워야 발광으로 읽히는데,
전장이 발광하면 아무것도 빛나지 않는다.

## 3. 원전 — 재질을 어디서 가져오나

배색사전(코퍼스 16쌍 · 씨앗 풀)은 1930년대 안료 견본이라 **발광도 금속도 말하지 않는다.**
11단계가 배색 구조를 `color-design` 스킬 본문에서 가져온 것과 같은 방식으로,
재질은 같은 스킬의 `references/light.md` 에서 가져온다.

| 재질 | 원전 문장 |
|---|---|
| 무광 / 광택 / 메탈릭 | "유리·금속처럼 매끈 → 강렬하고 **날카롭게** 맺힘 / 천·점토처럼 거칠고 무광 → 거의 안 나타나거나 **넓고 흐릿하게** 번짐" (1절 하이라이트 표) |
| 메탈릭의 하이라이트 | "하이라이트에는 **광원의 색이 그대로 실린다.** 주광부는 물체의 고유색을 밝게 드러내다 회색조가 되지만, 하이라이트는 물체 색과 무관하게 광원 색을 반사한다" (1절 하이라이트) |
| 발광 | "우리 눈에 보이는 모든 것은 광원이다. 빛을 받아서 반사하는 모든 표면은 주변으로 빛을 다시 발사하고 있다" (1절 암부 — 주변광과 반사광) |
| 발광이 주변을 물들이는 것 | "암부의 명도와 색은 `그 공간의 주변광 색 × 물체의 고유색` 이 상호작용한 결과다" (같은 절) |

**PBR 수치 규격의 출처는 다르다.** base color 범위(금속 180~255 · 비금속 50~243)는
언리얼 엔진의 Physically Based Materials 지침이다 `[문헌]` — 원전(`light.md`)에도
배색사전에도 없고, 이 저장소에서 인게임 실측으로 확인한 값도 아니다.
문서와 코드에 그렇게 태그해서 적는다.

## 4. 설계

### 4.1 진입점

```
applyFinish(역할색hex, finishId, 역할) → 머티리얼 한 벌
```

순수 함수. 화면·API·LLM 이 이 단계에 없는 이유는 11단계가 정확히 이 모양으로 성공했기
때문이다 — 그때 **측정이 설계를 세 번 바꿨고**, 화면을 먼저 붙였으면 그 세 번을 화면
뒤에서 찾았어야 했다.

### 4.2 재질 카탈로그 — `data/finishes.json`

**문자열만 들어간다.** `structures.json` 과 같은 규칙이다.

| id | 이름 | 원리 | source |
|---|---|---|---|
| `matte` | 무광 | 하이라이트가 거의 안 생기거나 넓고 흐릿하게 번진다(천·점토). 색은 중간톤에 있다 | light.md 1절 하이라이트 표 |
| `gloss` | 광택 | 매끈한 비금속. 하이라이트는 날카롭지만 고유색은 그대로 남는다 (젖은 아스팔트) | light.md 1절 하이라이트 표 |
| `metal` | 메탈릭 | 매끈해서 하이라이트가 날카롭게 맺히고, 거기에 물체 색이 아니라 광원 색이 실린다 | light.md 1절 하이라이트 |
| `emissive` | 발광 | 스스로 빛을 내어 주변 암부에 자기 색을 태운다 | light.md 1절 암부·주변광 |

넷으로 자른 근거는 PBR 이 실제로 가르는 축이 둘뿐이기 때문이다 — **금속인가(metallic)**,
**매끈한가(roughness)**. 발광은 그 둘과 직교하는 별도 채널이다. 여기에 더 얹으면
(벨벳·서브서피스·클리어코트) 엔진마다 셰이더가 갈려 "붙여넣을 수 있는 값"이 아니게 된다.

**이 파일에 숫자나 헥스가 생기면 규칙이 깨진 것이고, S16-G1 이 운다.**
러프니스를 몇으로 두는지는 원전에 없으므로 전부 `src/material.js` 한 곳에 있다.

### 4.3 파생 규칙 — `src/material.js` (숫자는 여기만)

출력 형태:

```js
{
  finish: "metal",
  baseColor: "#RRGGBB",              // sRGB
  metallic: 0 | 1,
  roughness: 0..1,                   // 언리얼 기준. Unity 변환은 4.5
  emission: null | { color: "#RRGGBB", ev: number }
}
```

- **`metallic` 은 0 아니면 1.** PBR 에서 중간값은 물리적으로 존재하는 재질이 아니다 —
  경계 픽셀을 블렌드하려고 있는 것이지 "반쯤 금속"이라는 물질이 있어서가 아니다.
  게이트(S16-G6)로 박는다.
- **`matte` · `gloss`**: base = 역할색 그대로, 비금속 범위(50~243)로 클램프.
  둘의 차이는 roughness 뿐이다.
- **`metal`**: 씨앗의 **색상각은 유지**하고 명도를 F0 구간으로 끌어올리며 채도를 누른다
  → min 채널 ≥180.
- **`emissive`**: base 는 어둡게(발광체는 꺼졌을 때 어둡다), `emission.color` 는 역할색의
  고채도 버전, `ev` 는 역할별.

#### 메탈릭 파생이 왜 필요한가 `[실측]`

코퍼스 32색을 PBR 규격에 대조했다.

```
금속 base 범위(min 채널 ≥180) 통과:  2개 — 아이보리 #F5ECC2, 살구 #FDD4BD
비금속 범위(50~243) 통과:           16개
base color 로 쓰기엔 너무 어두움(max<50): 2개 — 흑록 #0F1A14, 미드나잇블루 #051230
```

**씨앗 색을 그대로 메탈릭 base 로 쓸 수 있는 조합이 사실상 없다.**
자홍 #B73F74 를 Metallic=1 로 주면 "어두운 자주색 금속"이라는, 현실에 없는 물질이 된다.
금속의 base color 는 안료색이 아니라 **반사율(F0)** 이라 밝은 구간에만 존재하기 때문이다.
그러므로 메탈릭은 색을 끌어올리는 파생 없이는 성립하지 않고, 이 파생은 `expand.js` 의
기존 규칙과 방향이 반대라 `material.js` 로 분리한다.

#### 채도 상한 면제와 그 대가

11단계는 파생색의 지각 채도가 안료 상한(씨앗 풀 기준 0.871)을 넘지 못하게 막는 게이트
S11-G9 · S11-G10 을 갖고 있다. **네온은 정의상 그 위다.**

**`emission` 만 면제한다.** 임의 예외가 아니라 원전이 이미 나눠 놓은 구분이다 —
하이라이트와 발광에 실리는 것은 물체 색이 아니라 광원 색이고, **광원은 안료가 아니다.**
`baseColor` 는 어떤 재질에서도 면제되지 않는다.

**대신 면제한 자리에 EV 상한을 새로 문다(S16-G8).** 안 물면 상한이 그냥 사라진 것이고,
11단계에서 `#00ffee`(C=1.000) 사고를 만든 것이 정확히 그런 빈자리였다.

**EV 상한값 자체는 원전에 없다 `[판단]`.** 그렇게 태그해서 적고, 나중에 실측으로
대체할 자리라는 것을 코드 주석에 남긴다.

### 4.4 엔진 변환 — 내부 표현은 하나

언리얼과 유니티가 같은 값을 다른 이름으로 **반대로** 쓴다.

| | 언리얼 | 유니티 (Standard · URP Lit · HDRP) |
|---|---|---|
| 매끈함 | `Roughness` (0 = 거울) | `Smoothness` (1 = 거울) |
| 발광 | Emissive 핀에 곱하는 선형 배수 | HDR 색 피커의 `hex + Intensity(EV)` |

`Roughness 0.2` 를 유니티 Smoothness 칸에 붙여넣으면 **의도한 것의 정반대 재질**이 나온다.
조용히 틀리고, 붙여넣은 사람은 값이 뒤집혔다는 것을 모른다.

그래서 내부 표현은 언리얼 기준 한 벌로 두고, 화면·내보내기에서 엔진별로 변환해 보여준다.
**변환이 왕복하는지를 게이트로 박는다(S16-G9).**

### 4.5 이 단계의 기본 배정

게이트를 돌리려면 "어느 역할에 어떤 재질"이 하나는 있어야 한다.
구조 8개별 역할 기본 배정을 `material.js` 에 둔다 — 원전에 없는 값이므로 데이터가 아니라
코드다. **이게 곧 12-B 에서 Ollama 가 없을 때의 폴백이다.** 두 번 만들지 않는다.

## 5. 게이트 S16-G1 ~ G10

| | 검사 |
|---|---|
| G1 | `data/finishes.json` 에 숫자·헥스가 없다 (모든 필드가 문자열) |
| G2 | 파생이 결정론적 — 같은 입력이 같은 출력, `Math.random` 없음 |
| G3 | 코드에 상수 헥스가 없다 — 모든 색이 씨앗에서 계산된다 (정적 + 행위 양쪽) |
| G4 | 비금속 base 가 50~243 (씨앗 풀 전체 × 8구조 × 역할 전부) |
| G5 | 금속 base 가 min 채널 ≥180 이고 색상각이 씨앗에서 벗어나지 않는다 |
| G6 | `metallic` 이 0 또는 1 뿐 |
| G7 | **면제가 새지 않는다** — `emission` 이 아닌 자리는 여전히 안료 채도 상한을 지킨다 |
| G8 | **EV 가 상한 안** — 면제한 자리에 새 상한이 실제로 걸린다 |
| G9 | 엔진 변환 왕복 — `Smoothness = 1 − Roughness` 가 왕복해 제자리로 온다 |
| G10 | 불량 입력(잘못된 헥스 · 없는 finish id)에서 조용히 망가지지 않는다 |

**G7 과 G8 이 짝이다.** 하나만 있으면 면제가 구멍이 된다.

**게이트마다 뮤테이션으로 반응을 확인한다.** 11단계에서 S11-G4 가 처음엔 뮤테이션 하나를
놓쳤고(출력을 통째 문자열로 이어 비교해서), 자리마다 검사하도록 고쳐서 잡았다.
반응하지 않는 게이트는 통과해도 통과가 아니다.

## 6. 파일과 크기

| 파일 | 무엇 | 대략 |
|---|---|---|
| `data/finishes.json` | 신규. 재질 4개의 이름·원리·출처. 문자열만 | ~50줄 |
| `src/material.js` | 신규. 파생 규칙 + 엔진 변환 + 기본 배정 | ~180줄 |
| `scripts/check-stage16.mjs` | 신규. S16-G1~G10 | ~200줄 |
| `GATES.md` · `README.md` | 12단계 절 추가, 게이트 수 갱신 | ~30줄 |

**리뷰 300줄 규율을 넘는다는 사실을 여기 적어 둔다.** 제품 코드는 ~230줄로 안쪽이지만
게이트 스크립트를 합치면 ~460줄이다. 11단계도 같은 모양이었다.
검사 코드를 줄여서 규율 숫자를 맞추는 것은 본말전도라고 보고 넘기로 했다.
리뷰가 버거우면 게이트를 두 묶음(G1~G6 / G7~G10)으로 쪼개 12-A1 · 12-A2 로 나눈다.

|---|---|
| **재질을 구조에 못 박고 LLM 미개입** | 결정론적이고 게이트가 쉽지만, "네온 사인"과 "도자기 그릇"이 같은 구조를 뽑으면 같은 재질이 나온다 — 질의가 재질에 닿지 못한다. **다만 버리지 않고 12-A 의 기본 배정 = 12-B 의 폴백으로 흡수했다** |
| **재질도 BM25 코퍼스로 만들어 질의에서 직접 검색** | 어휘에는 가장 충실하다. 그러나 **재질 코퍼스에는 원전이 없다.** `data/seeds.json` 의 `_noProse` 가 "전사본이 주는 것은 헥스와 원명뿐, 나머지를 지어내면 틀린 근거 위에서 돈다"며 이미 같은 유혹을 거절해 뒀다. 여기서 뒤집으면 그 규율이 무너진다 |
| **헥스만 내고 스칼라는 사람이 정하게** | 범위가 작고 기존 계약을 거의 안 깨뜨린다. 그러나 같은 헥스를 Emission 에 넣었을 때 Intensity 에 따라 전혀 다른 색으로 보이는 것을 막을 수 없고, **게이트로 검사할 실체가 색뿐**이 된다 |
| **배색 한 장에 재질 하나** | 규칙이 단순하지만 "어둠 속 네온"을 못 만든다 (2절 참조) |
| **언리얼 기준 한 벌만 내고 라벨로 안내** | 구현이 작다. 그러나 뒤집기를 사람이 손으로 해야 하고, 놓치면 **조용히 반대 재질**이 된다 |
| **재질을 다섯 이상으로** | 벨벳·서브서피스·클리어코트는 엔진마다 셰이더가 갈려 "붙여넣을 수 있는 값"이 아니게 된다 |

## 8. 되돌리는 법

이 단계는 **기존 코드를 고치지 않고 더하기만 한다.** 되돌리려면 지운다.

1. `data/finishes.json` · `src/material.js` · `scripts/check-stage12.mjs` 삭제
2. `GATES.md` · `README.md` 의 12단계 절과 게이트 수를 되돌린다

S11 이하 게이트는 이 단계에 영향받지 않는다 — `material.js` 는 `expand.js` 의 출력을
입력으로 받기만 하고 그쪽을 수정하지 않는다. **다만 채도 상한 면제(4.3)를 나중에
`expand.js` 쪽으로 새게 두면 그때부터 되돌리기가 단순 삭제가 아니게 된다.**
S16-G7 이 그 누수를 막는 게이트다.

## 9. 열려 있는 것

### 9.1 ~~파생 결과의 바탕이 거의 흰색이다~~ — **해소됨 (15단계, 2026-09-07)** `[실측]`

스펙 자체검토 중에 발견했다. `expand.js` 의 명도 앵커는 `light: 0.93` 이고, 여덟 구조 중
일곱이 바탕을 그 앵커에 붙인다.

```
16쌍 × 8구조 = 128장 중 바탕 명도 l ≥ 0.90 인 것: 112장 (87.5%)

pair-06 (네온·사이버펑크 태그가 붙은 바로 그 조합):
  tone-on-tone     바탕 #e8eff3 l=0.93
  complementary    바탕 #eaeef1 l=0.93
  analogous        바탕 #e8f3f2 l=0.93
  value-scale      바탕 #eaeef0 l=0.93
  accent-by-chroma 바탕 #efebed l=0.93
  warm-neutral     바탕 #f2ebe8 l=0.93
  aerial           먼 쪽 #e9edf2 l=0.93
  tone-in-tone     바탕 #a71a59 l=0.38   ← 여덟 중 유일하게 어둡다
```

**"어두운 사이버펑크"의 '어두운'이 산출물에 없다.** 그리고 재질은 이것을 고치지 못한다 —
`applyFinish` 는 역할색을 받아 가공할 뿐 명도 위계를 다시 쓰지 않고, 다시 쓰게 만들면
배색 결정이 두 파일에 나뉘어 앉는다.

이것은 잘못이 아니라 전제다. 여덟 구조는 `color-design` 의 **웹·앱 UI 색 결정** 절에서
왔고, 거기서 바탕이 밝은 것은 기본값이다. 게임 씬은 전제가 다르다.

**그러므로 12-A 만으로는 원 요청이 충족되지 않는다.** 명도 방향을 뒤집는 조각이 따로
필요하고, 그 근거는 `light.md` 의 명도 그루핑에 있다 — "명부·중간톤·암부 중 **어느 덩어리가
가장 넓은 면적을 차지하는지** 파악한다."

**결정: 이 조각(12-A0)을 재질보다 먼저 만든다.** 순서를 뒤집으면 12-A 가 끝나도 원 질의로는
여전히 흰 바탕에 금속·네온이 얹힌 결과가 나와, 무엇이 맞고 무엇이 틀렸는지 눈으로 가릴 수 없다.
12-A0 은 `expand.js` 를 건드리므로 S11 게이트 10개에 대한 회귀 검사가 함께 간다.

### 9.2 그 밖에

- **EV 상한값에 근거가 없다 `[판단]`.** 인게임 블룸 실측으로 대체해야 한다.
- **PBR base color 범위(180~255 / 50~243)를 인게임에서 확인하지 않았다 `[문헌]`.**
  언리얼 문서 지침이고, 유니티에도 같은 값이 맞는지는 검증되지 않았다.
- **3색 이상의 면적 비율 규칙이 여전히 없다.** 11단계에서 열어 둔 항목이고
  12-C 의 주제다. `light.md` 의 **명도 그루핑**(명부/중간톤/암부 면적 배분)이 답을
  줄 것으로 보이지만 이번 단계에는 없다. **발광은 좁은 면적일 때만 발광으로 읽히므로,
  면적 규칙 없이는 12-A 의 결과가 화면에서 제대로 보이지 않는다.**
- `warm-neutral` 구조가 씨앗을 거의 안 타는 문제(11단계 기록)는 그대로다.
  재질이 그것을 가려 줄지 악화시킬지 모른다.
