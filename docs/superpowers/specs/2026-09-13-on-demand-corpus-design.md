# 검색 4단계 — 온디맨드: 코퍼스가 바뀌면 재시작 없이 반영되고, 바뀐 문서만 다시 임베딩한다

- 날짜: 2026-09-13
- 상태: 구현됨 (27단계, 2026-09-13)
- 근거 문서: `docs/com/rag-is-simpler-than-you-think.md` 의 4단계("문서 변동률 일 10% 이상일 때").
  **실측이 요구한 단계가 아니다** — 코퍼스 34건, 마지막 변경 9월 1~5일. 대표가 "미리 대응한다" 고 결정했다.
  그래서 범위를 작게 잡는다.

## 4단계가 이 저장소에서 뜻하는 것

문서의 4단계는 "질의 때 그 자리에서 임베딩" 이지만, 이 저장소는 애초에 **코퍼스를 기동 때 읽고 고정**한다
(`server.js` 머리 주석 · BM25 색인 · 관계 어휘 · `pipeline.palettes` 참조 여섯 자리). 문서가 바뀌어도 재시작
전엔 아무것도 모른다. 그러니 이 단계의 알맹이는 둘이다.

1. **코퍼스 변동 반영** — `data/palettes.json`·`data/diagnostics.json` 이 바뀌면 재시작 없이 색인·어휘·임베딩이 따라간다.
2. **문서별 임베딩 캐시** — 바뀐 문서만 다시 임베딩하고, 캐시를 디스크에 남겨 재시작해도 안 다시 만든다.

## 버린 대안

| 대안 | 왜 버렸나 |
|---|---|
| 파일 감시(`fs.watch`) | Windows 에서 이벤트가 중복·누락된다. 감시 프로세스가 있으면 게이트가 결정적이지 않다 |
| 명시적 재적재 요청(`POST /api/reload`) | "자동 반영" 이 아니다 |
| 서버 자동 재시작 | 진행 중 요청이 끊기고, 우리가 띄운 Ollama 자식 프로세스 소유권이 꼬인다. 임베딩을 매번 다시 만든다 |
| 임베딩 캐시만(코퍼스 고정) | 대표가 범위에서 뺐다 — 변동 반영이 없으면 4단계라 부를 수 없다 |
| 질의 시점 지연 임베딩(문서 그대로) | 34건에서 매 질의가 느려질 뿐 얻는 게 없다 |
| 씨앗 풀·구조 카탈로그·재질까지 재적재 | 검색이 아니다. 구조 카탈로그는 LLM 프롬프트가 이름을 그대로 써서 **요청 중에 바뀌면 안 된다**는 기존 결정이 있다 |

## 설계 1 — 코퍼스 변동 반영

| 무엇 | 어떻게 |
|---|---|
| 감지 | `pipeline.reloadIfChanged()` — 두 파일의 `mtimeMs`·`size` 를 `fs.statSync` 로 본다. **`CORPUS_CHECK_TTL_MS = 2000`** 안에는 한 번만. `/api/search` · `/api/status` · `/api/expand` 가 부른다 |
| 재적재 | 바뀌었으면 `loadPalettes`·`loadDiagnostics` 를 다시 불러 색인·어휘·`byId`·`embedDocs`·관계 어휘를 새로 만들고 `version` 을 1 올린다. 새 `embedDocs` 로 `embed.prepare()` 를 부른다(기다리지 않는다) |
| 깨진 파일 | 편집 도중 저장된 반쪽 JSON 이면 **옛 코퍼스를 그대로 쓰고** `corpusError` 에 사유를 남긴다. 다음 확인에서 고쳐져 있으면 회복하고 사유를 지운다 |
| 살아 있는 참조 | `server.js` 의 `relationVocab` 상수를 `pipeline.relationVocab` 로 옮긴다(재적재 때 다시 계산). `pipeline.palettes`·`diagnostics` 는 호출 시점에 읽으므로 속성 재할당으로 충분하다 |
| 경로 오버라이드 | `TONEFIRST_CORPUS_DIR` — 있으면 그 아래 `palettes.json`·`diagnostics.json`. 게이트가 `data/` 를 임시 폴더에 복사해 놓고 바꿔 가며 잰다. 서버가 실제로 그 경로를 쓰는지 게이트가 확인한다 |
| 상태 | `/api/status` 에 `corpus: {version, palettes, diagnostics, checkedAt, reloadedAt, error}`. 루프백 밖에서는 `error` 원문 대신 고정 문구 |
| 사다리 | `maxStage` — 임베딩 준비 + 재적재 가능이면 4. 재적재는 항상 가능하므로 실질적으로 임베딩 준비 시 4 |

## 설계 2 — 문서별 임베딩 캐시 (`src/embed.js`)

| 무엇 | 어떻게 |
|---|---|
| 키 | `sha1(model + "\n" + text)` (`node:crypto`). 문장이 한 글자라도 바뀌면 다른 키 |
| 메모리 | `Map<hash, number[]>`. `prepare(docs)` 는 **캐시에 없는 문서만** `/api/embed` 에 보낸다. 0건이면 호출 자체를 안 한다 |
| 디스크 | `${TONEFIRST_DATA_DIR ?? var}/embeddings.json` — `{model, dims, entries: {hash: number[]}}`. 임시 파일 → `rename` (`store.js` 관행). 읽을 때 깨져 있으면 `.corrupt-<time>` 으로 옆으로 치우고 빈 캐시로 시작 |
| 가지치기 | `prepare` 마다 **현재 문서의 해시만** 남긴다. 34건 × 1024차원 ≈ 300KB, 자라지 않는다 |
| 모델 변경 | 파일의 `model` 이 지금 모델과 다르면 캐시 전체를 버린다 |
| 상태 | `embed.status()` 에 `cached`(캐시에서 온 수) · `embedded`(이번에 새로 만든 수) 추가 |
| 옛 벡터 창 | 재적재 뒤 재임베딩이 끝날 때까지 `similarities` 는 옛 코퍼스 벡터를 낸다. **`pipeline` 의 `rerank` 가 `byId` 에 없는 id 를 버린다.** 창은 수십 ms |
| 저장 시점 | 새로 임베딩한 것이 하나라도 있을 때만 디스크에 쓴다. 쓰기 실패는 사유만 남기고 서비스는 계속 |

## 게이트 (27단계, 검사기가 구현보다 먼저)

| 게이트 | 쉽게 말하면 |
|---|---|
| G1 | 임시 코퍼스 폴더로 기동 → 팔레트 한 건의 요약을 고쳐 저장 → **다음 검색이 새 내용으로 잡힌다**(재시작 없이) · `version` 이 1 오른다. 양성 대조: 안 바꾸면 버전 그대로 |
| G2 | 바뀐 문서 **하나만** 다시 임베딩된다 — 스텁이 `/api/embed` 의 입력 건수를 센다(34 → 1) |
| G3 | 재시작해도 캐시가 살아 임베딩 입력이 **0건** · 모델명이 바뀌면 34건 전부 다시 |
| G4 | 깨진 JSON 을 저장해도 옛 코퍼스로 계속 답하고 `corpus.error` 에 사유 · 고치면 회복하고 `error` 가 `null` |
| G5 | 문서를 지우면 옛 벡터 창에서도 그 id 가 결과에 안 나온다 (스텁 임베딩을 느리게 해 창을 넓혀 잰다) |
| G6 | 캐시 파일이 깨져도 기동하고 옆으로 치운 뒤 새로 만든다 · 문서를 바꿔도 캐시 항목 수가 문서 수를 넘지 않는다 |
| G7 | `/api/status` `corpus` 필드 · 사다리 4칸(`maxStage`) · 루프백 밖에서 경로·사유 원문 숨김 · `TONEFIRST_CORPUS_DIR` 이 실제로 쓰인다 |
| 회귀 | S1 · S2 · S3 · S4 · S26 전체 |

## 되돌리는 법

`pipeline.reloadIfChanged()` 호출 셋을 빼고 `relationVocab` 을 상수로 되돌리면 코퍼스는 다시 기동 때
고정된다. 캐시는 `embed.js` 의 디스크 읽기/쓰기 두 함수를 빼면 26단계 동작(기동 때 전부 임베딩)이다.
`var/embeddings.json` 은 지워도 된다 — 다음 기동에 다시 만든다.
