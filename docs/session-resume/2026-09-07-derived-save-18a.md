# 2026-09-07 — 파생 팔레트 저장 (18단계 · 18-A)

남은 작업을 [`docs/com/open-work.md`](../com/open-work.md) 에 모으고, 사용자가 **A1(파생 팔레트
저장)** 부터 하기로 정했다. 이 문서는 그중 서버·저장소 절반(18-A)의 기록이다.

## 바뀌기 전에는 무엇이 있었나

13단계가 파생 팔레트를 화면에 그렸다. 펼치면 배색 구조 여덟 장이 나오고 슬라이더로 면적도
맞출 수 있다. **그런데 저장이 안 됐다.** 새로고침하면 사라진다.

13단계가 그것을 미룬 이유를 이렇게 적어 뒀다 — **"`normalizeRatio` 가 2색 전제다."**
실제로는 막힌 것이 셋이었다.

| 막힌 것 | 왜 |
|---|---|
| 파생이 코퍼스에 없다 | 저장은 `paletteId` 로 **코퍼스에서 색을 찾는다.** 파생은 계산으로 나온다 |
| 비율이 2색 전제 | `normalizeRatio(70)` → `[70, 30]`. 파생은 3~4색이다 |
| 항목 모양이 다르다 | 저장 항목에 `type`(D형)·`hueRelation`·`summary` 가 들어간다. 파생에는 그런 게 없다 |

## 어떤 원리를 썼나

### 화면이 색을 보내지 않는다 — 결정성이 코퍼스 자리를 대신한다

`src/store.js` 규칙 4 가 이미 적어 뒀다: **"화면이 보낸 색을 그대로 저장하면 저장소가 코퍼스와
어긋나기 시작한다."** 그래서 저장 요청에서 받는 것은 id·메모·비율뿐이고 색은 서버가 찾는다.

파생은 코퍼스에 없으니 그 규칙이 안 통하는 줄 알았는데, **다른 성질이 같은 자리를 대신한다** —
파생은 결정적이다(S11-G3). `씨앗 id + 구조 id + 모드` 셋만 있으면 서버가 **언제든 다시
계산할 수 있다.**

```
화면 → { seedId, structureId, mode, shares?, note? }
서버 → expandSeed(씨앗, 구조, { mode })  ← 색은 여기서 나온다
```

`S18-G1` 이 요청에 새빨간 거짓 색(`#ff0000` 등)을 실어 보내고, 저장된 색이 **게이트가 독립적으로
계산한 것과 정확히 같은지** 본다.

### 비율이 배열이 된다 — 13단계가 갈고리를 남겼다

`public/ratio.js` 의 `shareBounds` 주석에 이미 이렇게 적혀 있었다:

> 지금 파생 구조는 3~4색뿐이라 닿지 않지만, 이건 화면과 서버가 함께 쓰는 계산이고
> **다음 단계(다색 저장)에서 색이 늘면 조용히 깨진다.**

`normalizeShares(value, count)` 가 넷을 함께 문다 — 길이가 색 개수와 같다 · 전부 정수다 ·
각자 하한 이상이다 · **합이 정확히 100** 이다. 합이 100 이 아니면 스와치 바에 틈이 생기거나
마지막 색이 잘려 화면이 말하는 비율과 보이는 비율이 달라진다.

**2색이면 숫자 하나도 받는다.** 기존 경로(`ratio: 70`)가 그대로 살아야 한다 — `S18-G8` 이
그 회귀를 본다.

**하한은 `public/ratio.js` 와 같은 값을 독립적으로 적는다.** 읽어 오면 그쪽을 낮췄을 때 서버
검증도 함께 느슨해진다. 이 저장소가 같은 부류로 세 번 뚫렸다.

### 모드가 다르면 다른 항목이다

같은 구조라도 밝은 모드와 어두운 모드는 색이 다르다. 병합 키가 `씨앗 + 구조 + 모드` 셋이다.

## 게이트가 코드를 뚫었다

`S18-G3` 이 `{ structureId: ["complementary"] }` 를 통과시키는 것을 잡았다.

```
String(["complementary"]) === "complementary"   ← clip 이 강제 변환한다
```

`clip` 이 `String(value ?? "")` 를 하므로 **배열 하나짜리가 그대로 지나간다.** 17단계에서
리뷰어가 `Object.hasOwn` 의 키 강제 변환으로 같은 부류를 찾았다 — **두 번째다.**
규칙으로 적었다: **강제 변환하는 함수 앞에서는 타입을 먼저 본다.**

## 같이 닫은 것 — 2색 경로의 같은 구멍

`note: null` 결함을 고치고 나서 **`savePalette` 쪽도 같은 구멍이 있는지** 봤다.
`S8-G1`·`S8-G3` 이 `null` 을 안 본다 — 그쪽을 되돌려도 게이트가 조용했다(실측).

리뷰가 지적한 것은 파생 쪽뿐이지만 **같은 부류라 함께 닫았다.** `S8-G3` 에 `null` 과 양성
대조를 넣었고, 되돌리면 이제 잡힌다.

## 열려 있는 것

- **`/saved` 의 내보내기가 파생을 아직 모른다.** CSS·JSON 둘 다 2색 전제 필드를 쓴다.
  A2 가 그 자리다.
- **파생 항목이 200개 상한을 코퍼스 항목과 나눠 쓴다.** 파생을 많이 저장하면 코퍼스 저장이
  밀려난다. 지금은 상한이 멀어 안 닿지만 기록해 둔다.
- **저장된 색이 재계산과 갈라질 수 있다.** `src/expand.js` 를 고치면 옛 저장 항목의 색이
  지금 계산과 달라진다. `S18-G7` 은 **방금 저장한 것**만 대조하므로 그 드리프트는 못 본다.
  씨앗·구조·모드를 남겨 뒀으니 다시 계산할 수는 있다.

## 함정 기록

- **뮤테이션이 겨냥한 자리를 확인한다.** 같은 문자열이 여러 곳에 있으면 `replace(..., 1)` 이
  엉뚱한 데를 고치고, 살아남은 것이 게이트 구멍처럼 보인다. 이번에 두 번 겪었다.
- **강제 변환하는 함수 앞에서는 타입을 먼저 본다.** `clip`·`Object.hasOwn` 둘 다 걸렸다.
- **살아 있는 목록은 그 자리에서 갱신한다.** 안 그러면 커밋되는 순간 거짓말이 된다.
- **중복은 반드시 갈린다.** 40줄을 두 번 적었더니 그중 한 줄이 갈려 결함이 됐다.
