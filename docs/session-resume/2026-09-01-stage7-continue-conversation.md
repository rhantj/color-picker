# 2026-09-01 — 7단계: 대화 이어하기

[내보내기 문서](2026-09-01-stage6-export.md) 다음. 초안이 약속한 세 기능 중 마지막.

## 바뀌기 전에는 무엇이 있었나

대화는 **세션 경계**로만 묶였다. 새로고침하면 새 대화가 열리고, 내역 화면은 읽기 전용이라
지난 대화로 돌아갈 방법이 없었다. 내역이 기록일 뿐 작업의 일부가 아니었다.

## 그래서 코드가 이렇게 된다

| 자리 | 무엇 |
|---|---|
| 내역 · 대화마다 | **이어서 묻기** → `/?conv=<id>` |
| 내역 · 턴마다 | **다시 묻기** → `/?conv=<id>&q=<질의>` (홈에서 자동 실행) |
| 홈 | **이어 쓰는 중** 배너 — 제목·턴 수·LLM 호출 수, "내역에서 보기"(앵커), "새 대화로" |

| 파일 | 변화 |
|---|---|
| `server.js` | `/api/conversations?id=` — 대화 하나 조회, 없으면 **404** |
| `public/index.html` | 배너 |
| `public/app.js` | `?conv=`·`?q=` 처리, `ready` 프로미스, 실패 알림, 새 대화 버튼 |
| `public/history.js` | 이어서·다시 묻기 링크, 대화 블록 앵커 |
| `scripts/check-stage7.mjs` | **신규.** S7-G1~G4 |

## 두 가지를 명시적으로 정했다

### 없는 대화 id 는 404 다

빈 결과로 돌려주면 화면이 "이어 쓰는 중" 이라고 표시한 채 새 대화를 연다. 사용자는 자기 질문이
어디에 쌓이는지 잃는다. 저장소(`recordTurn`)는 모르는 id 를 받으면 새 대화를 여는데, 그 동작은
그대로 두고 **화면이 그 전에 걸러낸다.**

실측: `?conv=conv-none-none` → 배너 안 뜸,
"그 대화를 이어 쓸 수 없습니다 — 없는 대화다. 새 대화로 시작합니다." 뒤 URL 정리.

### 기록 실패를 더 이상 삼키지 않는다

전에는 `recordTurn(data).catch(() => {})` 였다. 검색을 막지 않으려는 의도였지만,
**이어 쓴다고 표시해 놓고 기록이 안 되면 사용자가 속는다.** 이제 배너에 사유를 쓴다.

## 코드 리뷰 (격리 복사본)

Critical 0 / High 0 / Medium 1 / Low 1. 둘 다 반영:

### [Medium] 대화 확인과 사용자 입력 사이의 경합

내가 의심한 지점(`?conv=`+`?q=` 순서)은 문제가 없었다 — `restoreFromUrl` 이 대화 조회를 `await`
한 뒤에 `run()` 을 불렀다. 진짜 구멍은 **사용자가 직접 검색하는 경우**였다.

리스너는 모듈 평가 중에 붙는데 대화 조회는 그 뒤에 끝난다. 그 사이(왕복 1회)에 사용자가 검색하면:

1. `conversationId === null` 인 채 기록 → **새 대화 A** 생성
2. 뒤이어 조회가 끝나 배너가 **대화 B** 를 보여줌

데이터가 사라지진 않지만 **화면이 가리키는 대화와 실제로 기록된 대화가 어긋난다.**

리스너 등록 순서를 바꾸는 대신 `ready` 프로미스를 두고 `run()` 이 그것을 기다리게 했다 —
등록 순서에 의존하면 나중에 진입점이 하나 더 생겼을 때 조용히 다시 깨진다.
`ready` 안에서는 `run()` 을 부르지 않는다(교착). 자동 실행은 `ready.then()` 에서 건다.

### [Low] 게이트가 정적 정규식이라 우회 가능

S7-G4 의 "기록 실패를 삼키지 않는다" 검사가 **정확히 옛 형태 하나만** 잡았다.
`.catch(() => undefined)` 로 바꾸면 그대로 통과했다 — 실제로 뮤테이션해 확인했다.

catch 본문이 화면에 무언가를 쓰는지(`textContent`)를 보도록 바꿨고, `run` 이 `ready` 를
기다리는지도 함께 검사한다. 두 뮤테이션 모두 이제 FAIL 로 잡힌다.

## 지금 상태

게이트 **46개 전부 통과** (S1 4 + S2 8 + S3 10 + S4 7 + S5 6 + S6 7 + S7 4).

| 뮤테이션 | 잡은 게이트 |
|---|---|
| 없는 대화를 빈 결과로 | `S7-G1_FAIL 없는 id 가 200` |
| id 필터 무시하고 전체 반환 | `S7-G1_FAIL 다른 대화가 왔다 / 전체 목록도 함께 왔다` |
| 이어 쓰기 실패를 조용히 넘김 | `S7-G4_FAIL 이어 쓸 수 없을 때 알리지 않는다` |
| `await ready` 제거 | `S7-G4_FAIL run 이 대화 확인(ready)을 기다리지 않는다` |
| 기록 실패를 `undefined` 로 삼킴 | `S7-G4_FAIL 기록 실패를 화면에 알리지 않는다` |

브라우저 실측: 2턴 대화 → "이어서 묻기" → 배너 `2턴 · LLM 0회` → 검색 → 같은 대화 3턴(대화 수 1).
"다시 묻기" → 입력 채워지고 자동 실행 → 4턴. "새 대화로" → 배너 사라지고 URL 이 `/` 로.
`?conv=` 로 이동한 **직후 곧바로** 검색해도 같은 대화에 붙는다.

**게이트가 못 보는 것:** 경합의 좁은 창 자체는 재현하기 어렵다(로컬 왕복 수십 ms).
정적 검사(`run` 이 `ready` 를 기다리는지)와 코드 구조로 막았고, 행위 검증은 갈라지지 않는다는
관찰까지다.

## 다음에 할 일

초안이 약속한 것은 다 채웠다. 남은 것은 위생 항목과 새 방향이다.

1. **저장 메모 입력 칸.** 서버는 이미 `note` 를 받고 내보내기에도 실리는데 화면에 입력이 없다. 작다.
2. **알려진 한계**
   - 저신뢰 질의가 동시에 오면 LLM 을 각각 부른다(단일 비행 없음).
   - 대화·저장·내보내기가 무인증 GET 이다. 루프백 바인딩이 유일한 방어다.
   - `LIMITS.saved`(200)는 중복 저장을 막아 코퍼스 크기(16)가 상한이라 도달 불가.
   - 대화 경계가 세션이라, 같은 대화를 두 탭에서 열면 각자 이어 쓴다(마지막 쓰기가 이긴다).
3. **새 방향 후보**
   - 검색 3단계(하이브리드)는 **아직 필요 없다.** 문서의 기준대로 실측이 요구할 때 올린다.
   - 진단 결과에서 팔레트로 넘어가는 연결("그럼 어떤 조합?").
   - 조합 비교 화면 — 두 조합을 나란히 놓고 면적을 바꿔 보는 것.
