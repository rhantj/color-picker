## 무엇을 했나

`POST /api/saved/note` 를 새로 두고 `/saved` 카드의 읽기 전용 문단을 편집 칸으로 바꿨다.
빈 값과 공백만 있는 값은 **지우기**다 — 화면에서 메모를 지우는 길이 이걸로 처음 열린다.

| 자리 | 무엇 |
|---|---|
| `src/store.js` | `updateSavedNote(id, note)` — 기존 `updateSavedRatio` 와 같은 모양 |
| `server.js` | 라우팅 한 줄. `handleWrite` 안이라 출처 검사를 물려받는다 |
| `public/saved.js` | `noteField()` — blur 에서 저장, 값이 바뀐 경우만 |
| `public/app.css` | 죽은 `.card__note` 를 편집 칸 규칙으로 교체 |

**저장 시점을 blur 로 잡은 이유** — 비율이 슬라이더에서 손을 뗄 때 저장하는 것과 같은 모양이다.
글자마다 보내면 요청이 쏟아지고, 버튼을 따로 두면 비율만 자동인 이유를 사용자가 알 수 없다.

### 리뷰어 둘이 정면으로 갈렸고 실측이 갈랐다

`security-reviewer` 는 "`input.disabled` 라 재진입 불가", `typescript-reviewer` 는 "`disabled` 를
세팅만 하고 가드로 읽지 않는다" 였다. 브라우저에서 재 봤다.

```
수정 전 — in-flight 중 disabled: true, note 요청 횟수: 2
수정 후 — note 요청 횟수: 1
```

**`typescript-reviewer` 가 맞다.** 브라우저가 포커스를 막는 것과 핸들러가 가드하는 것은 다르다.
다만 실사용 경로로는 재현이 어렵다 — 진짜 브라우저에서는 disabled 된 입력에 다시 포커스를 못 준다.
구조적 위험이지 관측된 사용자 결함은 아니다. **이 저장소가 홈 화면에서 이미 같은 형태로 겪었다.**

### S9-G6 을 만든 이유 — 검증이 아니라 그 아래 불변식을 지킨다

파괴 시험에서 `ID_SHAPE` 검증을 빼 봤는데 **어떤 게이트도 안 잡았다.** 처음엔 게이트 결함으로
의심했지만, 이 경로에서 `wanted` 는 `find()` 동등 비교에만 쓰이고 파일 경로 조립에 안 들어가서
검증을 빼도 없는 항목으로 거부된다 — **관측 가능한 동작이 같다.** 리뷰어 둘이 각각 코드 추적과
실행으로 확인했다.

그래서 검증 자체는 게이트로 못 박을 수 없다. 대신 **그것이 유일 방어가 되는 조건**을 막았다 —
id 가 경로 조립·동적 프로퍼티 접근·값 혼입 어디로도 안 간다는 불변식이다. 그 셋을 각각 넣어
게이트가 잡는 것을 확인했다.

## 배운 것

**게이트가 안 잡았다고 게이트를 먼저 의심하지 않는다.** 이 세션에서 파괴 시험이 두 번 헛돌았다.
한 번은 바꾼 줄이 이미 `serialize` 콜백 안이었고, 한 번은 위처럼 검증이 유일 방어가 아니었다.
**시험이 실제로 그 조건을 만들었는지부터 본다.**

**게이트 수를 두 곳에 적는 구조가 계속 어긋난다.** `README.md` 와 `GATES.md` 본문 양쪽에 있고,
이번에 "알려진 한계" 절 **안**의 수치를 두 번 놓쳤다. 점검 대상에 본문 서술까지 넣어야 한다.
