# 24단계 — 명도로 가른다고 한 배색은 본문이 읽힌다 (C1)

## 한 줄

**바탕 위에 놓인 본문 글자가 안 읽히는 배색이 나가고 있었다.** 80건 중 62건. 원인은
그 색이 앉은 자리가 **어떤 색으로도 기준에 못 닿는 자리**였기 때문이고, 자리를 옮겼다.

여기서 80건은 **씨앗 40쌍 × 밝은/어두운 모드 2** 다. 씨앗 40쌍은 배색사전 코퍼스 16쌍과
씨앗 풀 24쌍을 합친 것이고, **둘 다 실제로 서비스에서 펼쳐진다.**

---

## 바뀌기 전에는 무엇이 있었나

작업 목록의 C1 은 이렇게 적혀 있었다.

> 파생색끼리의 대비를 안 본다. 밝은 모드 243건 · 어두운 모드 169건이 바탕 대비 3:1 미만.
> **잘 안 보이는 배색이 나가고 있다.**

먼저 그 수부터 다시 쟀다. **수는 맞았다.** 그런데 어디에 몰려 있는지를 보니 처방이
달라졌다.

---

## 왜 처방을 바꿨나 — 일괄 규칙은 기법 하나를 지운다

`tone-in-tone` 이라는 배색 구조가 있다. 카탈로그가 그것을 이렇게 정의한다.

> 명도·채도를 **고정하고** 색상만 가로로 움직인다.

명도를 고정하면 대비(=명도 비율)는 1:1 근처에 머문다. 그러니까 **그 구조의 낮은 대비는
고장이 아니라 기법이 작동하는 모습**이다. 8구조 전부에 3:1 을 걸면 이 기법이 사라진다.

그래서 **구조가 스스로 무엇을 약속했는지**로 갈랐다. 카탈로그 설명문을 읽어 셋으로 나눈다.

| 갈래 | 쉽게 말하면 | 어떤 구조 | 무엇을 요구하나 |
|---|---|---|---|
| ① 명도로 가른다 | "여기 글자 올려도 된다" 고 스스로 말한 것 | `tone-on-tone` · `value-scale` | 본문이 **읽혀야 한다** |
| ② 명도를 고정한다 | 낮은 대비가 곧 기법 | `tone-in-tone` | **요구하지 않는다.** 오히려 낮은 채로 남는지를 본다 |
| ③ 말이 없다 | 대비를 약속도 금지도 안 한 것 | 나머지 다섯 | 아무것도 요구하지 않는다 |

## 원리 — 앵커가 애초에 못 닿는 자리였다

이 저장소는 파생색의 명도를 **앵커 다섯 자리**에 앉힌다.

```
light 0.93   upper 0.72   mid 0.50   lower 0.32   dark 0.15
```

`tone-on-tone` 의 본문이 `mid` 에 있었다. 바탕은 `light` 다. 이 둘의 대비를 **순수 회색으로**
계산하면 — 즉 채도를 0까지 빼서 가장 유리하게 만들면 — **최대 3.37:1** 이다.

**4.5 는 어떤 색으로도 못 닿는다.** 색을 어떻게 고르든 실패한다. 구조적이었다.

대조군이 있었다. `value-scale` 은 *"명·중·암을 확보하면 가독성 문제가 대부분 여기서
끝난다"* 고 **같은 것을 약속**하는데 32건 전부 통과한다. 그쪽 본문은 `lower` 에 있다
(회색 기준 6.67:1). **같은 약속을 한 둘이 갈렸으니 "이 기법은 원래 그렇다" 가 아니다.**

---

## 그래서 코드가 이렇게 된다

`src/expand.js` 두 군데.

**① 본문을 `mid` → `lower` 로.** 명도 단계가 0.93 → 0.32 → 0.15 가 된다. 인접 간격이
0.61·0.17 이라 `S11-G7`(최소 0.15)을 지킨다.

**② 닿지 않으면 채도만 뺀다 (`readable`).** 앵커를 옮겨도 색상에 따라 못 닿는 경우가 남는다.
**HSL 의 명도는 사람이 느끼는 밝기가 아니기 때문**이다 — 같은 l=0.5 에서 노랑의 휘도는
0.510, 파랑은 0.081 로 여섯 배 넘게 갈린다 `[실측]`.

```js
function readable(hsl, groundHex) {
  const at = (s) => hslToHex({ ...hsl, s });
  if (contrastOf(at(hsl.s), groundHex) >= TEXT_CONTRAST) return hsl;   // 읽히면 손대지 않는다
  if (contrastOf(at(0), groundHex) < TEXT_CONTRAST) return { ...hsl, s: 0 };
  let lo = 0, hi = hsl.s;                                              // 회색 쪽으로 이분 탐색
  for (let i = 0; i < 24; i += 1) { /* … */ }
  return { ...hsl, s: lo };
}
```

- **색상(h)도 명도(l)도 안 건드린다.** 씨앗의 색을 잃지 않고, 앵커가 정한 단계도
  안 흐트러뜨린다. 채도만 회색 쪽으로 민다.
- **반드시 닿는다.** 회색이 앵커 간격만큼의 대비를 내므로 목표가 그 안에 있다.
- **80건 중 9건만 손댄다.** 나머지 71건은 이미 읽혀서 그대로 나간다 `[실측]`.
- **매직 넘버가 없다.** 4.5:1 은 WCAG 2.2 일반 크기 글자 기준 `[문헌]`이고, 이 저장소가
  스와치 글자색에 이미 쓰던 값이다(`S2-G5`·`S13-G6`).

`value-scale` 에도 같은 것을 걸었다. **오늘은 무동작이다** — 80건 전부 이미 4.71 이상이라
헥스가 한 글자도 안 바뀐다. 그래도 거는 것은 **약속이 구조에 붙어 있지 씨앗 목록에 붙어
있지 않기 때문**이다. 씨앗이 더 늘거나 앵커를 조정하면 여기도 못 닿는 색이 온다.

## 게이트가 저를 두 번, 리뷰가 세 번 교정했다

**① `aerial` 을 잘못 분류했다.** 원리가 *"먼 쪽은 대비·채도를 낮추고"* 라 ②(평평한 구조)에
넣었는데 `S24-G3` 이 **중앙값 4.75 로 가르고 있다**고 잡았다. 다시 읽으면 그것은 **층끼리의
상대 순서**를 말하는 것이지 절대적으로 평평하다는 말이 아니다. ③으로 옮겼다.

**② `S15-G8` 이 이 변경을 잡았다.** `mid` 는 밝음↔어두움 거울의 **고정점**이라 그 자리 색은
두 모드에서 같았고, 그 게이트가 그것을 지키고 있었다. 본문이 `lower` 로 가면서 두 모드가
갈리는데 **그게 맞다** — 어두운 바탕에는 밝은 본문이 놓여야 한다. 전에는 두 모드가 같아서
어두운 모드 대비가 3.02 까지 내려갔다. `MID_FIXED` 를 `aerial`/중간 하나로 줄였다.

**③ 게이트가 씨앗의 40%만 보고 있었다.** `S24-G1`·`G2` 가 `data/palettes.json`(코퍼스
16쌍)만 읽었는데, `check-stage15.mjs` 는 같은 자리에서 `allSeeds()`(코퍼스 + 씨앗 풀
24쌍)를 쓴다. **씨앗 풀은 이미 `/api/expand` 로 나가고 있다**(`S12-G6`). 오늘은 우연히
40쌍 전부 안전했지만(최소 4.5017), 앵커를 건드리면 풀 쪽에서만 깨져도 게이트가 조용했을
자리다. 40쌍 전부를 보게 고쳤고, `loadSeeds` 가 파일 손상 시 빈 배열로 물러서는 것도
**조용히 코퍼스만 보게 되는 경로**라 막았다.

**④ `S24-G6` 의 핵심 검사가 죽은 코드였다.** 아래 "기준선을 통째로 다시 만들지 않았다"
절에 따로 적었다.

**⑤ 대비 공식이 저장소에 세 벌 있었다.** `public/color.js` 에 있고, `src/expand.js` 가
같은 파일에서 `chroma` 는 가져다 쓰면서 대비만 **다시 구현**해 두었고, 게이트가 또 한 벌
갖고 있었다. `src/expand.js` 쪽을 지우고 `contrast` 를 import 하게 했다 — 기준선이 한
글자도 안 바뀌었으므로 **두 구현은 같은 값을 내고 있었다**(`S15-G1` 통과로 확인).

**게이트 쪽 한 벌은 일부러 남긴다.** 그것은 감시 대상과 독립이어야 하고, `S24-G5` 가 두
구현을 문헌 값 6개와 파생색 1360건에서 대조한다 — 차이는 **정확히 0** 이다 `[실측]`.

## 기준선을 통째로 다시 만들지 않았다

`scripts/fixtures/expand-baseline.json` 은 "예전과 같은 결과가 나오는가" 를 보는 파일이고,
그 파일이 스스로 이렇게 경고한다.

> 다시 만들면 게이트가 아무것도 검사하지 않게 된다.

그래서 **바뀐 줄만 갈고**, 옛 값 40개를 `_revisions` 에 이유·범위와 함께 남겼다.
`S24-G6` 이 그 기록이 정직한지 본다.

1. 기록한 구조는 **실제로** 옛 값과 다른가 (안 바꿔 놓고 바꿨다고 적지 않았는가)
2. **기록에 없는 칸은 옛 값 그대로인가** — "이것만 바꿨다" 를 기계가 확인한다
3. 이유와 범위가 적혀 있는가
4. 색상(h)이 보존됐는가 — 엉뚱한 구조 이름을 적으면 여기서 걸린다

### 2번은 처음에 거짓말이었다

**리뷰 두 곳이 각자 뚫었다.** 기록에 없는 구조(`complementary` / `value-scale`)의 앵커를
바꾸고 기준선을 다시 만들었는데 이 게이트가 정상 메시지를 그대로 냈다. 코드를 보면
검사할 목록을 `_revisions` 에서 만들어 놓고 같은 `_revisions` 를 훑고 있었다 —
**조건이 언제나 참인 죽은 코드**였다.

**고치면서 알게 된 것은, 이 파일만 봐서는 원리적으로 못 잡는다는 것이다.** 파일 안에는
'안 바꾼 구조의 옛 값' 이 없다. 통째로 다시 만들면 기록도 같이 다시 쓸 수 있으니, 무엇을
넣어도 자기 자신을 근거로 자기를 증명하는 꼴이 된다. **바깥의 고정점이 필요하고, 이
저장소에 있는 것은 git 이력뿐이다.**

그래서 게이트가 **이 파일이 태어난 커밋을 git 에게 물어서** 고정점으로 삼는다.

```
git log --diff-filter=A --format=%H -- scripts/fixtures/expand-baseline.json
  → d7f84e3958cde1881b5241e9f91bc1702b05af6c
```

그 커밋의 기준선을 꺼내 지금 파일과 320칸을 대조하고, 달라진 칸이 기록에 없으면 운다.

**고정점을 기록에서 읽으면 안 된다는 것은 2차 리뷰가 알려줬다.** 처음엔 기록에 적은
`baseSha` 를 고정점으로 썼는데, 리뷰어가 이렇게 뚫었다 — **몰래 재생성한 커밋을 먼저
만들고**, 그 위에 정당한 수정을 올린 뒤, `baseSha` 로 자기가 만든 그 커밋을 가리킨다.
둘 사이의 차이가 0 이니 조용히 통과한다.

같은 저장소 상태에서 **고정점의 출처만 바꿔** A/B 로 확인했다 `[실측]`.

```
고정점을 기록이 고르게 두면 → 통과 (뚫림)
고정점을 git 에서 구하면    → 실패 "기록에 없는 칸 40개가 d7f84e3 이후 바뀌었다"
```

**이 저장소가 게이트마다 지키는 규칙을 제가 거기서 어긴 것이었다** — 감시 대상에서 값을
가져오지 않는다. 문턱도 분류도 다 그렇게 두고 있었는데, 고정점 하나를 그 파일 안에서
읽었다. `baseSha` 는 남겨 두되 **적힌 옛 값이 진짜인지 보는 용도**로만 쓴다.

변형 7개로 확인했다 `[실측]`.

| 변형 | 결과 |
|---|---|
| 기록에 없는 `value-scale` 앵커를 바꾸고 기준선 320칸 재생성 | `S15-G1` 은 통과, **`S24-G6` 이 "기록에 없는 칸 40개가 바뀌었다" 로 운다** |
| 기록한 옛 값을 다른 색으로 위조 | 운다 (색상 검사) |
| 기록한 옛 값을 **색상은 유지한 채** 위조 | 운다 (git 대조) |
| `baseSha` 를 지움 | 운다 |
| `baseSha` 를 없는 커밋으로 | 운다 |
| 기록에서 씨앗 하나를 빼고 그 칸은 바뀐 채로 둠 | 운다 |
| **재생성을 먼저 커밋하고 고정점을 그 커밋으로 옮김** (2차 리뷰가 찾은 것) | 운다 — 고정점을 git 에서 구하게 고친 뒤 |

**첫 줄이 핵심이다** — 리뷰어들이 재현한 그 경로가 이제 막힌다.

**남는 구멍도 적는다.** git 이력을 못 읽는 곳(얕은 클론 등)에서는 통과가 아니라
**실패**한다. 이력 자체를 다시 쓰면 고정점이 바뀌지만, 그것은 픽스처 하나를 조용히 갈아
끼우는 것과는 다른 종류의 일이고 흔적이 남는다.

| **C2** | 기준선 파일 재생성 방어 | **거의 닫혔다** — `baseSha` + git 대조로 "기록 없이 통째로 다시 만들기" 가 잡힌다 `[실측]`. 남은 것은 *재생성을 커밋한 뒤 `baseSha` 를 옮기는* 경로뿐이고, 그것도 커밋 시점에 게이트가 운다 |
| **D1** | Ollama 오류 문구가 거짓말한다 | 작다 |
| **D2** | 폭 0 공백(U+200B)을 못 거른다 | 작다 |

**게이트로 못 만든 것 하나를 남긴다** — `aerial` 의 "층끼리 먼 쪽이 덜 대비된다" 는 상대
