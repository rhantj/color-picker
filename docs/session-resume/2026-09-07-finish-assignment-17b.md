```

질의는 **"네온 사인 빛의 어두운 사이버펑크 풍의 색감"**. 진짜 Ollama 가 그것을 읽고 강조에
발광을 붙였다. 같은 코드가 "가을 카페 브랜딩" 에는 다른 배정을 낸다 — **그것이 이 단계의 전부다.**

## 결정 하나를 사용자에게 물었다

재질 수치(base·metallic·roughness·emission)를 어떻게 줄 것인가. 기존 내보내기(`/api/export`)는
저장된 2색 조합용이고 파생 팔레트 저장은 13단계가 미뤄 뒀으니 집이 없었다. 선택지 둘을 크기와
함께 제시했고 **사용자가 "배정만 내려보내고 카드에 재질 이름만" 을 골랐다.**

| | 응답 크기 | 골랐나 |
|---|---|---|
| 배정만 + 이름 | 3.8KB → **4.2KB** (실측) | ○ |
| 수치까지 | 3.8KB → 약 12KB | × |

**안 쓰는 것을 보내지 않는다.** 화면이 그리는 것은 이름뿐이다. `S17-G9` 가 응답에
`roughness`·`metallic`·`baseColor`·`emission`·`smoothness` 가 없는지 검사한다 — 수치가
필요해지면 그때 별도로 붙인다.

**이름은 서버가 `id→이름` 표로 보낸다.** 화면이 한글 이름을 박으면 `data/finishes.json` 을
고쳐도 안 따라오고, 그 어긋남을 아무도 안 알려 준다. `S17-G12` 가 코드에 이름이 박히는 것을 막는다.

## 두 LLM 호출을 나란히 부른다

`/api/expand` 가 이제 모델을 두 번 부른다 — 구조 선택과 재질 배정. 서로의 결과를 안 쓰므로
기다릴 이유가 없다.

```

  구조 선택 1475ms
  재질 배정  902ms

**진짜 Ollama 에서도 이득이 났다.** 모델 하나를 두 요청이 나눠 쓰므로 내부적으로 줄을 설 수
있다고 걱정했는데, 실측은 병렬이 실제로 겹쳤다. 다만 `S17-G10` 이 무는 것은 **우리 코드가
불필요하게 기다리지 않는다**는 것까지다 — 엔진 내부 스케줄링은 우리가 통제하지 않는다.

## 이 변경이 결함 둘을 드러냈다

### ① `ollama.js` `refresh()` 의 경쟁 조건 — 3단계부터 있던 것

`S17-G10` 이 **"모델 호출 1회"** 로 실패했다. 둘을 불렀는데 하나만 닿았다.

```js
// 고치기 전
if (Date.now() - lastProbeAt < STATUS_TTL_MS) return status();
lastProbeAt = Date.now();      // ← await 앞에서 세운다
const models = await probe();  // ← 이게 끝나기 전에 두 번째 호출이 들어오면
```

두 번째 호출이 TTL 검사에 걸려 **아직 끝나지 않은 탐지의 낡은 상태**를 받는다. 기동 직후에는
그것이 `"unknown"` 이라 호출부가 "Ollama 를 쓸 수 없다" 로 물러선다 — **재질 배정이 첫 요청마다
조용히 폴백했다.**

```
고치기 전: Promise.all([refresh(), refresh()]) → ready / unknown
고친 뒤:                                        → ready / ready   (fetch 1회)
```

**순차 호출만 있던 3단계~16단계 동안에는 드러날 수 없던 결함이다.** 진행 중 탐지에 합류하는
빗장(`probing`)을 넣었다. 3단계 게이트 10개 회귀 0.

리뷰어가 이 결함을 **독립적으로 재현**해 확인했다 — 패치를 되돌려 `ready / unknown` 을 보고,
다시 적용해 `ready / ready` 를 봤다.

### ② `S14-G6` 이 깨졌다 — 내가 만든 회귀

그 게이트는 `STRUCTURE_TIMEOUT_MS` 만 700 으로 낮추는데, LLM 호출이 둘이 되면서 재질 쪽
기본값(20초)이 남았다. `Promise.all` 이 느린 쪽을 기다려 **8040ms** 가 걸렸다.

두 타임아웃을 함께 낮추도록 고쳤다. **게이트를 푼 것이 아니라 대상이 둘이 된 것에 맞췄다** —
요청 전체가 4초 안에 끝나는지를 보는 강도는 그대로이고, 하나만 낮춰서 통과시키는 쪽이 오히려
느슨하다. 기본값(둘 다 20초)에서는 전과 같다.

**응답 시간이 두 타임아웃 중 느린 쪽에 묶인다**는 사실을 `GATES.md` '알려진 한계' 에 적었다.
합이 아니라 최대다(직렬보다 낫다). 다만 한쪽만 낮추면 다른 쪽 기본값이 남는다.

- **병렬화는 순차 시절에 숨어 있던 경쟁 조건을 깨운다.** `refresh()` 가 그랬다. 공유 상태를
