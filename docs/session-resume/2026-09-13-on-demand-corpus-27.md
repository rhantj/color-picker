# 2026-09-13 — 검색 4단계 온디맨드: 코퍼스가 바뀌면 재시작 없이 따라간다 (27단계)

## 무엇을 했나

문서(`docs/com/rag-is-simpler-than-you-think.md`)의 4단계는 "문서가 자주 바뀌는 곳에서 그때그때 임베딩" 이다.
이 저장소는 코퍼스 34건이 기동 때 고정돼 있어 **실측이 요구한 단계는 아니다**(마지막 변경 9월 1~5일).
대표가 "미리 대응한다" 고 결정했고, 그래서 범위를 작게 잡았다.

| 무엇 | 쉽게 말하면 |
|---|---|
| 코퍼스 변동 반영 | 검색 요청이 오면(2초에 한 번만) `palettes.json`·`diagnostics.json` 의 시각·크기를 본다. 바뀌었으면 그 자리에서 다시 읽어 BM25 색인·어휘·관계 어휘를 새로 만든다. 깨진 파일이면 옛 코퍼스를 지키고 사유만 남긴다 |
| 문서별 임베딩 캐시 | `sha1(모델 + 문장)` 이 키. 캐시에 없는 문서만 Ollama 에 보낸다. `var/embeddings.json` 에 남겨 재시작해도 안 다시 만든다. 현재 문서 해시만 남겨 자라지 않는다 |
| 옛 벡터 창 | 재적재 뒤 재임베딩이 끝날 때까지 옛 벡터가 온다. 지금 코퍼스에 없는 id 는 결합에서 버린다 |

설계와 버린 대안: `docs/superpowers/specs/2026-09-13-on-demand-corpus-design.md`. 계획: `docs/superpowers/plans/2026-09-13-on-demand-corpus.md`.
이 단계부터 프로젝트 `CLAUDE.md` 에 "구현도 unlazy 로" 순서를 적었다.

### 캐시가 생기며 26단계 하네스가 헛돌았다

`S26-G3` 이 "모델 없음인데 ready" 로 실패했다. 26단계 검사기의 자식 프로세스가 기본 `var/` 에 임베딩 캐시를
쓰고, 다음 자식이 그것을 읽어 Ollama 를 부르지 않고도 `ready` 가 됐다. 게이트가 저장소 `var/` 를 더럽히기도
했다(스텁 벡터가 든 `embeddings.json`). 자식·서버마다 임시 `TONEFIRST_DATA_DIR` 을 주도록 고쳤다.
**저장 계층이 하나 늘면 그것을 모르는 옛 검사기가 어디를 더럽히는지 봐야 한다.**

## 함정 기록

- **스텁 벡터로는 1단계·1위를 단정할 수 없다.** 3차원 해시 벡터라 정확 매칭에 절대 동의하지 않고 서로 다른
  문장이 코사인 0.997 로 붙는다. G4 의 "1단계 · pair-10" 단정을 "계속 답하는가" 로 바꿨다.
- **검색으로 재적재를 일으키면 질의 임베딩 1건이 섞여 세어진다.** 건수를 재는 게이트(G2·G6)는 `/api/status`
  로 재적재를 일으킨다.
- **캐시 히트는 창을 없앤다.** 삭제만 있으면 임베딩 호출이 0 이라 옛 벡터 창이 없다 — 그래서 창을 재려면 변경이
  함께 있어야 한다.
