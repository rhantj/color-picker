# 2026-09-06 — 씨앗을 40쌍으로 (12단계: 씨앗 전용 풀)

[씨앗 조합을 배색 구조로 불리기(11-A)](2026-09-06-seed-expansion.md) 다음. 요청은 한 줄이었다 —
"프리뷰에 있는 16개의 시드 외에 다른 시드도 **있으면** 추가해줘, 상한은 40개로".

## 먼저 "있으면" 을 확인했다 — 없었다

원전 파일과 코퍼스를 헥스·쌍 단위로 대조했다.

| 대조 | 결과 |
|---|---|
| 원전 `~/.claude/skills/color-design/references/palettes.md` | **16쌍이 전부** (`### ①`~`⑯`, 헥스 32개) |
| 코퍼스에 빠진 원전 색 / 쌍 | 없음 / 없음 |
| 원전에 없는 코퍼스 색 / 쌍 | 없음 / 없음 |

원전 첫 줄이 `# 검증된 2색 조합 16쌍` 이고 출처가 "와다 산조 『배색사전』에서 **블랙스완이 추린
16개**, 헥스는 영상 화면의 색상 카드를 직접 읽은 값" 이다. **원서 전체가 아니라 영상용 부분집합**
이고 우리는 그걸 다 갖고 있었다. 늘리려면 새 출처가 필요했다.

## 왜 그냥 못 넣나 — 해설은 계산되지 않는다

`S1-G1` 이 요구하는 필드는 `id`·`name`·`type`(A~D)·`summary`·`impression` 이고, 색인은
`hueRelation`·`toneRelation`·`tags` 도 쓴다. 공개 전사본이 주는 것은 **헥스와 원명뿐**이다.

"분류만이라도 계산하면 되지 않나" 를 재 봤고, 안 된다.

```
원전이 '보색' 이라 적은 7쌍의 색상각: 114 122 146 149 166 177 177
원전이 '유사색' 이라 적은 6쌍의 색상각:  32  50  60  70  79 132

보색 최솟값 113.8  <  유사색 최댓값 132.2   ← 구간이 겹치고 뒤집힌다
```

`pair-06`(유사색 132도)이 `pair-07`(보색 114도)보다 더 벌어져 있다. **원전의 분류는 각도가 아니라
큐레이터의 판단이다.** 지어내면 `S10` 의 진단→조합 연결이 그 문자열을 그대로 대조하므로 조용히
틀린 연결이 생긴다.

## 그래서 고른 것 — 검색되는 코퍼스와 씨앗 풀을 나눈다

사용자에게 네 갈래를 제시하고 **씨앗 전용 풀**을 골랐다.

| | `data/palettes.json` (16쌍) | `data/seeds.json` (24쌍) |
|---|---|---|
| 담는 것 | 헥스 + 유형·관계·인상 해설 | **헥스와 원명만** |
| 출처 | 배색사전에서 블랙스완이 추린 16개 | 원서 공개 전사본(348조합) |
| BM25 색인 | **들어간다** | **안 들어간다** |
| 쓰임 | 검색 + 씨앗 | **씨앗만** |

해설을 지어내지 않으면서 씨앗을 40개로 만드는 유일한 길이다. 색인에 안 넣는 이유는 두 가지다 —
해설이 없어 자연어 질의로 잡힐 근거가 없고, 억지로 넣으면 색 이름 하나로 걸려 16쌍의 정답을
밀어낸다.

### 출처가 같은 책이라는 것을 실측으로 확인했다

전사본은 다른 사람이 다른 경로로 옮긴 것이라 값이 어긋날 수 있다. 겹치는 부분을 대조했다.

- 조합 **#1** `English Red #D96629 + Cerulian Blue #0093A5` = 우리 `pair-03` — **헥스가 정확히 일치**
- 조합 **#5** `Cossack Green #437742 + Vandar Poel's Blue #064F6E` = 우리 `pair-13` — 일치
- 120개 2색 조합 중 **14개**가 코퍼스 16쌍과 헥스까지 일치
- 코퍼스 원명 29개 중 **24개**가 전사본에 존재

## 어떻게 24개를 골랐나

규칙을 `data/seeds.json` 의 `_howPicked` 에 적어 뒀다. 재현 가능해야 다음 사람이 다시 뽑을 수 있다.

1. 348조합 중 **2색 조합 120개**만.
2. 코퍼스와 **쌍이 같거나 색을 하나라도 공유하는 것 제외** — 색을 공유하면 파생 결과가 겹친다.
3. **강조색의 지각 채도가 코퍼스 하한 미만인 것 제외** (아래).
4. 남은 68개에서 **강조색 색상각 30도 구획 라운드로빈**, 조합 번호가 작은 것부터.

4번이 필요한 이유는 실측이다. 번호순으로 앞에서 24개를 자르면 12구획 중 **5개가 비고 한 구획에
9개가 몰린다.** 라운드로빈은 빈 구획이 3개이고, 그 3개는 후보 자체에 색이 없는 구간이다.

색상환 30도 구획 12칸에 후보가 각각 몇 개씩 들어가는지 센 것이다.

```
후보 전체(68)      14 25  4  0  0  2  7  3  0  1  2 10   빈 구획 3
번호순 앞 24        2  9  2  0  0  0  2  2  0  0  2  5   빈 구획 5
라운드로빈 24       4  3  3  0  0  2  3  3  0  1  2  3   빈 구획 3
```

**이 규칙만 보고 다시 돌리면 파일의 24개가 그대로 나온다**(재현 확인). 사람이 손으로 고른 것이
아니라는 뜻이고, 상한을 40에서 올리고 싶으면 같은 라운드로빈을 이어 돌리면 된다.

## 게이트를 넓히자마자 하나가 걸렸다

S11 게이트가 코퍼스 16쌍만 보고 있었다. 씨앗 풀 24쌍은 **아무 게이트도 없이 화면에 나갈 뻔했다.**
`allSeeds()`(16 + 24 = 40쌍)로 넓혔더니 곧바로 `wada-069` 가 걸렸다.

```
S11-G6 실패 — wada-069 톤온톤이 색상을 80.0도 움직였다 / wada-069 보색이 107도다
```

씨앗이 `Warm Gray #A1A39A + Black #111314` 로 **둘 다 사실상 무채색**이었다(지각 채도 0.035,
0.012). 파생된 밝은 바탕이 순회색으로 반올림되며 색상각이 0으로 읽힌 것이다 — **색상이 없는 색에서
색상각을 재면 그런 값이 나온다.**

**게이트를 느슨하게 하는 대신 씨앗을 뺐다.** 회색의 "보색대비" 는 결과가 나쁜 게 아니라 이름이
틀린 것이기 때문이다. 하한은 내가 고르지 않고 **코퍼스가 이미 그은 선**을 읽는다 — 코퍼스 16쌍의
강조 채도 최솟값 **0.176**. 후보 69개 중 이 조건에 걸린 것은 `#69`(0.035) 하나뿐이고 그다음으로
낮은 후보는 0.188 이라 경계가 붙어 있지 않다.

`S11-G9` 의 지각 채도 상한도 코퍼스가 아니라 **원전 전체**(코퍼스 32색 + 씨앗 48색)에서 읽도록
바꿨다. 씨앗 색이 코퍼스보다 쨍하기 때문이다 — `Yellow Orange #F99D1B` 가 0.871 로 코퍼스 최대
0.729 를 넘는다. 코퍼스만으로 재면 **원전 색을 결함으로 잡는다.**

## 그래서 파일이 이렇게 된다

| 파일 | 무엇 |
|---|---|
| `data/seeds.json` | **신규.** 씨앗 24쌍 + 출처·선정 규칙을 `_` 필드로 |
| `src/seeds.js` | **신규.** `loadSeeds` / `seedLabel`. 던지지 않고, 해설이 섞인 항목을 걷어낸다 |
| `scripts/check-stage12.mjs` | **신규.** S12-G1~G6 |
| `scripts/check-stage11.mjs` | S11 게이트를 40쌍으로, G9 상한을 원전 전체로 |
| `GATES.md` · `README.md` | 12단계 절, 게이트 76 → 82 |

화면에 쓸 이름(`Yellow Orange × Dark Tyrian Blue`)은 **데이터에 저장하지 않고 `seedLabel()` 이
조립한다.** 저장하면 원전이 말한 이름처럼 보인다 — `public/ratio.js` 가 면적을 데이터에 안 넣는
것과 같은 이유다.

`loadSeeds(path)` 가 경로를 인자로 받는 이유는 게이트 때문이다. "파일이 깨져도 도는가" 를 검사하려면
깨진 파일이 필요한데, 경로가 고정이면 게이트가 저장소의 `data/seeds.json` 을 직접 망가뜨려야 하고
검사 중에 죽으면 저장소가 깨진 채 남는다.

격리 worktree 둘에서 `typescript-reviewer` 와 `code-reviewer` 를 돌렸다.

두 번째 리뷰어는 `_howPicked` 의 선정 알고리즘을 **원본 데이터에서 독립 재구현**해 24개 조합
번호가 정확히 일치함을 확인했고, 24쌍의 원명·헥스를 전사본과 대조해 불일치 0건을 보고했다.

### 금지 목록을 허용 목록으로 바꿨다

처음엔 코퍼스 쪽 필드 이름을 나열해 막았다(`summary`·`impression`·`type`·…). 두 가지가 틀렸다 —
**색 안쪽을 안 봤고**, 금지 목록은 앞으로 생길 필드를 못 막는다. 스키마가 닫혀 있고 작으므로
허용 목록이 맞다. 씨앗은 `{id, no, colors}`, 색은 `{origName, hex}` 만 통과한다.

**`S12-G5` 의 테스트 헬퍼에 `colorExtra` 인자가 이미 있었는데 11개 케이스 중 아무도 안 채웠다.**
구멍을 검사할 준비가 돼 있었는데 쓰지 않은 것이다. 색 안쪽 케이스 넷을 채웠다.

### `S11-G10` — 전역 상한 하나로는 부족했다

`S11-G9` 는 원전 전체에서 읽은 상한 하나로 본다. 그래서 **씨앗이 늘면 상한도 올라간다.**
씨앗 풀이 들어오며 0.729 → 0.871 이 됐고, G9 가 만들어진 계기였던 톤인톤 회귀(0.776)가
그 아래로 들어갔다. 게이트를 넓혔더니 게이트가 느슨해진 것이다.

씨앗별 상한을 여덟 구조 전부에 걸 수는 없다. 40쌍 실측:

| 구조 | 자기 씨앗을 넘는 씨앗 수 | 최대 초과폭 |
|---|---|---|
| 톤온톤 | 31/40 | +0.341 |
| 공기원근 | 15/40 | +0.290 |
| 유사색대비 | 12/40 | +0.239 |
| 명도 스케일 | 5/40 | +0.047 |
| 보색대비 | 3/40 | +0.039 |
| **톤인톤** | **2/40** | **+0.004** (8비트 반올림) |
| **강조색** | **0/40** | — |
| **따뜻한 뉴트럴** | **0/40** | — |

밝기를 옮기는 구조가 더 쨍해지는 것은 **그 구조가 하는 일 자체다.** 넘지 않아야 하는 것은
**톤 좌표를 씨앗에서 그대로 가져오는 셋**이고, 그 셋만 씨앗별로 본다. 허용치 0.02 는
반올림(+0.004)의 다섯 배이고 과거 회귀(+0.070)의 3분의 1 아래다 — 두 값 사이가 비어 있다.

뮤테이션으로 확인했다. 톤인톤 회귀를 되살리면 **G9 는 통과하고 G10 이 `+0.071` 로 잡는다.**

## 배운 것

**게이트의 검사 범위를 넓히면 게이트가 느슨해질 수 있다.** S11 을 16쌍에서 40쌍으로 넓힌 것은
옳았다 — 안 넓혔으면 새 24쌍이 무검사로 나갔다. 그런데 같은 변경이 `S11-G9` 의 상한을
데이터에서 읽는 구조 때문에 0.729 에서 0.871 로 올려, **그 게이트가 만들어진 계기였던 회귀를
못 잡게 만들었다.** "코퍼스에서 읽어 값이 굳지 않게 한다" 는 좋은 규칙인데, 그 값이 **느슨해지는
방향으로만** 움직일 수 있으면 감도를 잃는다. 데이터에서 읽는 상한은 **넓힐 때 감도를 다시 재야 한다.**

**재구성**해서 봤기 때문이다 — 뮤테이션은 `createSearcher()` 를 고쳤으니 게이트 눈에 안 띈다.
**게이트가 보는 것과 서버가 쓰는 것이 달랐다.** `createSearcher()` 를 직접 보고 헥스로 실제 검색까지
하도록 고쳐서 잡았다. 양성 대조 둘도 함께 넣었다 — 없으면 "검색이 아무것도 못 찾는" 상태로도
통과한다.

**`S12-G2` 의 첫 판이 거짓 양성도 냈다.** 씨앗의 색 이름 `Black` 이 코퍼스 원명 `Blackish Olive`
안에 부분 문자열로 들어 있었다. 이 저장소가 전에 겪은 "한 글자 태그(`독`·`숲`)가 다른 낱말 안에서
걸린다" 와 같은 부류다. **이름은 원서가 재사용하므로 애초에 결정적 증거가 아니다** — 유일한 헥스로만
본다. `indexText` 가 언제나 헥스를 함께 넣으므로 색인 유입은 반드시 헥스로 드러난다.

## 함정 기록

- **`node -e '...'` 안의 한국어 문자열에 작은따옴표를 쓰면 셸이 문자열을 끊는다.**
  `S11-G6 이 '톤온톤이...' 로 잡았다` 를 쓰다가 `Unterminated string constant` 로 죽었다.
  `docs/troubleshootings/2026-09-01-tooling-traps.md` 1번과 같은 부류다 — **긴 한국어 문자열이
  들어가는 패치는 `node -e` 로 하지 않고 스크립트 파일로 쓴다.**
- **`review-fanout.sh --round` 는 양의 정수만 받는다.** 이 저장소는 1~6 이 이미 고정돼 7을 썼다.

## 다음에 할 일 — 11-B 는 그대로다

1. `src/structure.js` — LLM 이 8구조 중 질의에 맞는 5개를 고르고 순서를 매긴다. Ollama 가 없으면
   카탈로그 앞 5개로 물러선다.

   조회해야 한다** — 이번에 풀이 생겼으므로 조회 자리가 둘이다. 클라이언트가 준 색은 믿지 않는다.
3. 화면 — 결과 카드에서 5장을 펼친다.
4. **3색 이상의 면적 비율 규칙을 먼저 정한다** (11-A 문서와 같은 항목, 아직 미결).
   `public/ratio.js` 는 2색이 아니면 균등 분할로 물러서는데, 이 저장소는 "비율 없는 5:5 칩은
   거짓말" 이라고 적어 뒀다. 제안은 역할이 비율을 정하게 하는 것(바탕 60 / 면 25 / 본문 10 / 강조 5).
