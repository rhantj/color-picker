# 2026-09-07 — 재질(PBR 머티리얼) 엔진 (16단계)

같은 날 세 번째 작업이다. [명도 방향(15단계)](2026-09-07-value-direction.md) →
[어두운 모드 토글](2026-09-07-dark-mode-toggle.md) → **재질 엔진**. 원 요청이
"네온 사인 빛의 어두운 사이버펑크 풍의 색감 + 이미션·메탈릭 같은 감촉" 이었고, 앞 둘이
'어두운' 을 만들었다. 이 단계가 '감촉' 을 만든다. **사슬이 여기서 닫힌다.**

## 바뀌기 전에는 무엇이 있었나

산출물이 **헥스 + 면적 %** 뿐이었다. 자홍과 진파랑을 50:50 사각형으로 늘어놓으면 사이버펑크가
아니라 그냥 두 색이다. 네온으로 읽히게 하는 것은 헥스가 아니라 어두운 바탕 · 좁은 면적 ·
번지는 빛인데, 그 셋을 담을 자리가 없었다.

게임 엔진에서 쓴다는 것이 확인되면서 요구가 정확해졌다 — **PBR 에서 메탈릭과 러프니스는 헥스가
아니라 0~1 스칼라**이고 이미션은 헥스 + 세기다. 헥스로 표현되는 것은 Base Color 뿐이다.

## 무엇이 나오나

```
[보색대비] pair-06 자홍 × 진파랑 · 어두운 모드
  바탕     #1f282e → 무광     base #323b41  metallic 0  Roughness 0.85
  본문     #90c3df → 광택     base #90c3df  metallic 0  Roughness 0.2
  강조     #8d3200 → 발광     base #5a4032  발광 #ff5a00 EV 4
```

어두운 무광 바탕 · 반사 있는 표면 · **좁은 면적 하나만 빛난다.** 강조의 몸체 base 가 어두운
것이 핵심이다 — 꺼졌을 때 어두워야 켰을 때 발광으로 읽힌다.

## 어떻게 나눴나

설계는 [스펙](../superpowers/specs/2026-09-07-pbr-material-finish-design.md)에 고정돼 있었다.
이번 세션이 새로 정한 것은 **어디서 자를까** 하나다. 스펙이 예상한 ~460줄을 넘겨서(약 1100줄)
300줄 리뷰 규율에 안 맞았고, 자른 자리는 **채도 면제**다.

| | 무엇 | 왜 여기서 자르나 |
|---|---|---|
| **16-A** | 무광·광택·메탈릭 + G1~G6·G10 | **면제가 없다.** S11 안료 상한이 그대로 성립해 검증이 단순하다 |
| **16-B** | 발광 + 면제·EV 상한(G7·G8 **짝**) + 엔진 변환(G9) + 기본 배정(G11) | 스펙이 "하나만 있으면 면제가 구멍" 이라고 못 박았다. **둘을 함께 들일 수 있을 때 들였다** |

두 조각을 한 커밋으로 올린다(사용자 결정).

## 스펙의 실측을 다시 재서 새 사실을 찾았다

이 저장소는 표본을 전체로 옮겨 적는 오류를 두 번 겪었으므로 `[실측]` 은 전수로 다시 잰다.
**스펙의 코퍼스 주장은 정확히 맞았다** (금속 범위 2개 · 비금속 16개 · 채도 상한 0.8706).

**그런데 스펙은 코퍼스만 봤다.** `applyFinish` 의 실제 입력은 **파생 역할색**이다.

| | 금속 범위(min≥180) | 비금속 범위(50~243) |
|---|---|---|
| 코퍼스 32색 | 2 (6%) | 16 (50%) |
| 파생 역할색 1000 (밝은) | 284 (28.4%) | 653 (65.3%) |
| 파생 역할색 1000 (어두운) | 134 (13.4%) | **531 (53.1%)** |

**어두운 모드에서 절반이 범위 밖이다.** 바로 앞 작업이 어두운 모드를 화면에 내보낸 직후라
이 숫자가 실제 의미를 갖는다. 게이트도 코퍼스가 아니라 **역할색 2000장**(두 모드)을 돈다.

## 어떤 원리를 썼나

### 1. 채널별 clamp 가 아니라 아핀 사상

```
채널별 clamp:  #0f1a14 → (50,50,50) = 회색           ← 색상각이 통째로 사라진다
아핀 사상:     #0f1a14 → #323d37, h=147.27도 그대로
```

`c' = k·c + b` (k>0) 는 채널 **차의 비**를 보존한다. HSL 색상각이 그 비로 정해지므로
(분자·분모가 같은 k 로 곱해진다) 색상각이 정확히 남는다. 대신 채도가 k 배로 줄고 명도가
옮겨간다 — 그것이 "물질의 범위 안으로 들어온다" 의 실제 내용이다. **실측 최대 이동 0.750도**
(허용 1.5, 8비트 반올림 몫).

`newLo` 를 원래 최저값에 가장 가깝게 잡아 **이미 창 안인 색은 한 채널도 안 움직인다.**

**재질마다 창이 다르고, 그 차이가 곧 재질의 정의다.**

```
matte · gloss   50~243   실재하는 비금속의 반사율 범위      [문헌]
metal          180~255   금속 base 는 안료색이 아니라 반사율(F0)  [문헌]
emissive        50~90    발광체는 꺼졌을 때 어둡다            [판단]
```

### 2. 금속은 색을 끌어올리는 파생 없이 성립하지 않는다

금속의 base color 는 안료색이 아니라 **반사율(F0)** 이라 밝은 구간에만 존재한다. 자홍 #B73F74
을 그대로 Metallic=1 로 주면 "어두운 자주색 금속" 이라는, 현실에 없는 물질이 된다.

### 3. 채도 면제는 `emission` 하나뿐이고, 그 대가로 EV 를 묶는다

11단계는 파생색의 지각 채도가 안료 상한(0.8706)을 못 넘게 막는데 **네온은 정의상 그 위다.**
임의 예외가 아니라 원전이 이미 나눠 놓은 구분이다 — 하이라이트와 발광에 실리는 것은 물체
색이 아니라 광원 색이고 **광원은 안료가 아니다.**

```
전 재질 baseColor 최대 지각채도   0.7569  (상한까지 여유 0.1137)  ← 면제가 안 샌다
emission 이 상한을 넘는 장          522/2000                    ← 면제가 실제로 일한다
```

**면제한 자리에 EV 상한을 새로 문다.** `EV_MAX = 4` 이고 가장 밝은 역할(강조)이 거기 딱
붙어 있다 — 여유를 두면 상한이 아무것도 안 묶는다. 값에는 근거가 없다 `[판단]`.

### 4. 엔진 변환에는 반올림이 필수다

언리얼 `Roughness`(0=거울)와 유니티 `Smoothness`(1=거울)는 같은 값을 **반대로** 쓴다.
그런데 `1 - (1 - x)` 가 x 로 안 돌아온다 — 0~1 을 0.001 간격으로 재면 **1001개 중 335개**가
어긋나고 이 저장소의 `gloss` 값 0.2 가 그중 하나다(0.19999999999999996). 오차는 5.6e-17 로
무시할 크기지만 **사람이 엔진 칸에 붙여넣을 값**이라 그런 꼬리가 보이면 안 된다.

## 뮤테이션

16-A 24종 + 16-B 22종을 돌렸다. **살아남은 것은 둘이고, 둘 다 구멍이 아님을 증명했다.**

| 살아남은 것 | 판정 | 근거 |
|---|---|---|
| 발광 채도 이득 1.6 → 1.0 | **등가 아님, 약화일 뿐** | 면제가 여전히 작동한다(108/2000 초과). `[판단]` 상수를 게이트로 못 박으면 동작이 아니라 표기를 지키게 된다 |
| `evForRole` 의 `Object.hasOwn` 약화 | **이중 방어에 가림** | `applyFinish` 의 바깥 검사가 먼저 잡는다. 실측: `EV_BY_ROLE["__proto__"]` 는 객체를, `toString` 은 함수를 준다 |

그리고 **뮤테이션이 진짜 구멍을 하나 찾았다.** EV 표가 `강조: EV_MAX` 로 상한을 참조해서,
상한을 99 로 올리면 강조도 함께 99 가 되어 "상한에 닿는다" 가 그대로 성립했다 —
**둘이 함께 움직이면 상한이 아무것도 안 묶는다.** 표를 리터럴로 떼어냈다.

게이트도 하나 잡았다. `fromUnity` 가 `finish` 를 되돌리는 척했고 왕복 게이트가 8000건 전부
실패했다 — **엔진 표기에 없는 것을 되돌릴 수 있는 척한 것**이다. 재질 이름은 우리 개념이다.

## 격리 리뷰 네 건 — 16-A 두 건, 16-B 두 건

### 16-A: Critical 0 · High 1 · Medium 1 · Low 3

| 지적 | 조치 |
|---|---|
| **High** — `S16-G1` 의 `source` 예외가 **순수 정수**를 못 막는다. `"1절 180 이상 반사율 근거"` 통과 | **블랙리스트 → 화이트리스트.** `<한두 자리>절` 만 허용 + 판정기 자체 대조 8건 |
| **Med** — `loadFinishes` 가 손상 JSON 에서 원시 `SyntaxError`. **주석은 이미 "StructureError 와 같은 자리다" 라고 말하고 있었다** | `loadStructures` 와 같은 모양으로 래핑 + 손상 5가지 게이트 |
| Low ×3 | 중복 호출 제거 · 캐시는 설계대로 유지 · 무채색 컷오프 기록 |

### 16-B: Critical 0 · High 2 · Medium 3 · Low 1

| 지적 | 조치 |
|---|---|
| **High (두 리뷰어가 각각 찾음)** — **발광체가 어둡다는 불변식에 게이트가 0개.** `EMISSIVE_BASE_MAX` 를 90 → 243 으로 바꾸면 몸체가 밝아지는데(`#ffe4a1` → `#f3d895`) **열한 게이트가 전부 통과** | `S16-G4` 를 **네 재질 전부**로 다시 씀. 재질별 창 + 재질별 양성 대조 |
| **High** — 게이트가 `DIELECTRIC_MIN/MAX`·`METAL_MIN` 을 **자기가 감시할 대상에서 import** 한다. `METAL_MIN` 을 1 로 바꾸자 `S16-G5` 가 `min >= 1` 을 찍으며 **통과** | 게이트에 독립 사본(`EXPECTED`) + `assertConstants` |
| **Med** — `role` 에 타입 검사가 없어 `{toString:()=>"강조"}` 와 `["강조"]` 가 통과 | `typeof` 검사 추가 + 게이트 3가지 |
| **Med** — 엔진 변환 함수에 입력 검증 없음. `roughness: 1.5` → `smoothness: -0.5`, `"0.2"` → 조용한 타입 변환 | `assertMaterial` 등 추가 + 게이트 14가지 |
| **Med** — 색상각 보존을 **문서는 보편 성질로 말하는데 게이트는 금속만** 본다. 비금속 창에서만 새게 하면 12.33도 틀어져도 전부 통과 | `S16-G5` 를 네 재질 전부로 확대 |
| Med — 16-B 세션 문서 없음 | **이 문서.** 16-A 문서를 16단계 전체로 다시 씀 |

**High 2 번이 가장 아프다.** 나는 `EV_MAX` 에 대해 정확히 그 교훈을 주석으로 적어 놓고
(`같은 값을 독립적으로 적는다`) **나머지 세 상수에 일반화하지 않았다.** 하필 그 셋이
`[문헌]` 인용값이라 조용한 표류를 가장 막고 싶은 자리였다.

리뷰어가 낸 변형 넷을 그대로 재현해 지금은 전부 잡히는 것을 확인했다.

```
발광 몸체가 밝아짐          → G4 G7 이 잡음
METAL_MIN 을 1 로           → G4 G5 G7 이 잡음
DIELECTRIC_MIN 을 10 으로   → G4 G7 이 잡음
비금속 창에서만 채널별 clamp → G5 가 잡음 (범위는 지켜지고 색상각만 무너지므로 G5 가 맞다)
```

## 열려 있는 것

- **러프니스·EV·기본 배정에 근거가 없다 `[판단]`.** 인게임 블룸·하이라이트 실측으로 대체할
  자리다. `EV_MAX = 4` 는 상한이 헐겁지 않게 표의 최댓값에 붙여 둔 값이라, 바꾸려면
  **표와 상한과 게이트 사본 세 곳**을 함께 고쳐야 한다(그 마찰이 의도된 것이다).
- **base color 범위를 인게임에서 확인하지 않았다 `[문헌]`.** 언리얼 문서 지침이고 유니티에도
  같은지 검증되지 않았다. 게이트는 "이 범위를 지키는가" 를 볼 뿐 **범위 자체가 옳은지는
  검사하지 않는다.**
- **내부 표현은 언리얼 기준이다.** 유니티로 보낼 때 `toUnity()` 를 안 거치면 정반대 재질이
  되고, **그것은 게이트가 막을 수 없다.**
- **엔진 변환 왕복은 입력이 소수 셋째 자리 안일 때만 정확하다.** `0.1234` → `0.123`.
  지금 값 넷이 전부 셋째 자리 안이라 안 닿는다.
- **화면·API·LLM 이 없다.** 17단계에서 LLM 이 질의를 보고 역할별 재질을 배정한다.
  `DEFAULT_FINISH_BY_ROLE` 이 그때의 폴백이다 — 두 번 만들지 않는다.

(13·14단계) — 새로 만드는 것이 아니라 그 위에 얹는다.

`selectStructures` 가 `matched` 로 "모델이 실제로 몇 개를 보탰나" 를 화면에 넘기는 것처럼,
재질 배정도 **무엇이 골랐는지 밝혀야 한다.** 폴백을 "LLM 이 골랐다" 로 말하면 배지가 거짓말한다.

## 함정 기록

- **게이트가 감시할 상수를 감시 대상에서 import 하면 안 된다.** 문턱이 함께 움직여 아무것도
  검사하지 않게 된다. 이 저장소에 이미 같은 규율이 있었는데(`check-stage15` 가
  `MIN_TIER_GAP` 을 다시 적는다) 나는 `EV_MAX` 에만 적용하고 나머지에 안 했다.
- **게이트 예외는 화이트리스트로 판다.** 블랙리스트로 팠다가 리뷰에 뚫렸다.
- **주석이 계약을 선언하면 게이트가 그것을 물어야 한다.** "StructureError 와 같은 자리다" 를
  적어 놓고 래핑을 안 했다.
- **문서가 보편 성질이라고 말하면 게이트도 보편적으로 물어야 한다.** 색상각 보존을 `fitRange`
  전체의 성질로 써 놓고 금속만 검사했다.
- **살아남은 뮤테이션을 곧바로 게이트 구멍으로 읽지 않는다.** 등가일 수도, 이중 방어에 가린
  것일 수도 있다. 가르는 방법은 전수 대조와 호출 그래프 확인이다.
- **Windows 에서 Python 게이트 러너의 출력이 cp949 로 죽는다.**
  `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` 를 먼저 부른다.
- **bash 히어독 안에 백틱·따옴표가 섞인 Python 을 넣으면 파서가 깨진다.** 스크래치패드에
  파일로 쓰고 `python <파일>` 로 부른다.
