# 2026-09-01 — Ollama 수명주기 (3단계 1/2)

[2단계 문서](2026-09-01-stage2-server-home.md) 다음. 질의 재작성 자체는 아직 없고, 그 앞에 필요한
**로컬 Ollama 확보**만 붙였다.

## 왜 이것부터인가

3단계는 로컬 LLM 을 쓴다. 그런데 Ollama 가 떠 있지 않으면 아무것도 안 된다. 사용자가 매번 손으로
`ollama serve` 를 치게 하는 방식은 반드시 잊힌다. 그래서 서버가 확인하고, 없으면 띄운다.

## 어떤 원리·제약을 썼나

프로세스를 띄우는 코드는 그 자체로 위험 표면이다. 안전 규칙 넷을 먼저 정하고 그 안에서 구현했다.

| 규칙 | 왜 |
|---|---|
| 사용자 입력이 spawn 에 닿지 않는다 | 질의 문자열이 프로세스 실행에 닿으면 그 자체가 취약점 |
| 이미 응답하면 새로 띄우지 않는다 | 사용자가 직접 띄운 인스턴스를 건드리지 않는다 |
| 단일 비행 | 동시 호출이 프로세스를 여러 개 띄우면 포트가 충돌 |
| 실패는 던지지 않고 상태로 남긴다 | Ollama 없이도 전문 검색은 돌아야 한다 |

종료 시 **우리가 띄운 것만** 정리한다(`startedByUs`). 사용자가 띄운 것은 우리 것이 아니다.

### 신뢰 경계를 명시했다

`OLLAMA_BIN`·`OLLAMA_HOST`·`PATH` 는 **신뢰 대상**이다. 이걸 바꿀 수 있는 사람은 이미 이 프로세스와
같은 권한으로 코드를 실행할 수 있으므로 여기서 막아도 얻는 게 없다. 특히 Windows 는 확장자 없는
실행 파일명을 현재 디렉터리에서 먼저 찾지만, 저장소에 `ollama.exe` 를 심을 수 있는 사람은 `server.js`
도 고칠 수 있다. **규칙 1 이 막는 것은 요청 데이터가 실행에 닿는 경로뿐이다** — 이걸 안 적으면
규칙이 실제보다 강해 보인다.

## 그래서 코드가 이렇게 된다

| 파일 | 무엇 |
|---|---|
| `src/ollama.js` | **신규.** `probe` / `ensureRunning` / `refresh` / `status` |
| `server.js` | 기동 시 비차단 `ensureRunning()`, `GET /api/status` |
| `public/index.html`·`app.css`·`app.js` | 상단 런타임 필이 실제 상태를 표시 |
| `scripts/check-stage3.mjs` | **신규.** S3-G1~G6 |

`ensureRunning()` 은 **띄울 수 있고**, `refresh()` 는 **확인만 한다**. 요청 처리 경로에서는
`refresh()` 만 부른다 — 요청이 프로세스 기동을 유발하지 않게 하는 경계다.

환경변수: `OLLAMA_HOST`(기본 `127.0.0.1:11434`), `OLLAMA_BIN`(기본 `ollama`),
`OLLAMA_AUTOSTART=0`(자동 기동 끄기), `OLLAMA_READY_TIMEOUT_MS`(기본 20000).

## 지금 상태 (실측)

| 상황 | 결과 | 걸린 시간 |
|---|---|---|
| 이미 떠 있음 | 확인만, `startedByUs: false` | 87ms |
| 죽어 있음 | 자동 기동 → ready, `startedByUs: true` | 5.0초 |
| 미설치 | `unavailable` + "ollama 을 찾을 수 없다", **검색은 그대로** | 즉시 |

화면 상단 필: `로컬 · Ollama 준비됨`, 점은 강조색, 툴팁 `127.0.0.1:11434 응답 · 모델 3개`.
**필의 이름은 여전히 `BM25`이고 사다리도 1단계만 칠해진다** — Ollama 가 준비돼 있어도 아직 검색에
쓰이지 않기 때문이다.

게이트 **17개 전부 통과** (S1 4 + S2 7 + S3 6).

## 보안 리뷰 (격리 복사본, security-reviewer)

Critical 0 / High 0 / Medium 4. 네 건 다 반영:

| 지적 | 조치 |
|---|---|
| **ready 로 굳는다.** 한번 ready 가 되면 Ollama 가 죽어도 `/api/status` 가 영원히 "준비됨" 으로 보고 | 읽기 전용 `refresh()` 추가(5초 캐시). 죽으면 `unavailable` 로 내려온다. **S3-G6 신설** |
| `/api/status` 가 모델 목록·호스트·오류 원문을 노출. `HOST=0.0.0.0` 이면 네트워크에 열린다 | 루프백 바인딩이 아니면 `state`·`startedByUs` 만 내보낸다 |
| S3-G5 정적 검사는 인자 이름만 바꿔도 우회된다 — 보안 통제로 보기 어렵다 | **맞다.** 정적 부분을 "회귀 스모크"로 성격 규정하고, **행위 검사**를 붙였다 — 자동 기동을 끈 채 죽은 호스트로 요청 24회를 퍼부어 프로세스가 뜨지 않음을 확인 |
| Windows PATH/CWD 바이너리 하이재킹 가능성, 완화·문서화 없음 | 절대경로 고정 대신 **신뢰 경계를 문서화**했다(위 절). 저장소에 파일을 심을 수 있으면 이미 코드를 고칠 수 있으므로 여기서 막는 것은 방어가 아니라 착시다 |

리뷰가 확인해 준 것: spawn 인젝션 경로 없음, SSRF 경로 없음, 단일 비행 패턴 정확, 종료 훅 중복 등록
방지 정확, 서버 기동을 막지 않음, 미처리 거부 경로 없음, 프런트 폴링이 20회에서 멈춤, XSS 없음.

|---|---|

11435 잔여 프로세스도 종료 훅이 정리했다.

## 함정 기록

- **S3-G6 의 첫 구현이 고정 대기 4초였다가 사전 조건에서 실패했다.** 외부 Ollama 가 4초 안에 안 뜨면
  그 사이 `ensureRunning` 이 자기 것을 띄우려 하고, 포트가 겹쳐 `unavailable` 이 된다. 폴링으로 바꿨다.
  **프로세스 기동을 고정 sleep 으로 기다리지 않는다.**
- `GATES.md` 에서 S3-G6 이 구현분과 미착수분에 **중복 배정**됐던 것을 잡아 미착수분을 G7~G9 로 밀었다.
