# 2026-09-06 — LLM 이 배색 구조 다섯을 고른다 (14단계 / 11-B-2)

[파생 팔레트를 화면에서 만지기(13단계)](2026-09-06-multicolor-ratio.md) 다음.
**이것이 원래 요청의 핵심이었다** — "LLM 이 rag 의 색 조합을 기반으로 여러 가지 색 조합을 보여주고,
가장 많이 쓰는 5개를 뽑아서 화면에 보여준다". 13단계까지는 여덟 장을 전부 보여줬고, 고르는 판단이 없었다.

## 왜 LLM 이어야 하나

8개 중 어느 다섯이 "가을 카페 브랜딩" 에 맞는지는 **계산으로 안 나온다.** 색상각도 명도도 그 판단을
못 한다 — 질문의 뜻을 읽어야 한다. 이 사이트에서 LLM 이 하는 일은 이제 둘이고(질의 재작성, 구조 선택)
둘 다 같은 성격이다: 전문 검색이나 산술이 못 하는 자리에서만 부른다.

## 경계 셋을 먼저 못 박았다

| 경계 | 왜 |
|---|---|
| **LLM 은 색에 닿지 않는다** | 고르는 것은 구조 id 뿐. 헥스는 `src/expand.js` 가 씨앗의 HSL 로만 만든다(S11). 모델이 뭘 뱉든 화면에 없는 색이 안 생긴다 — 사용자가 11-A 에서 고른 경계다 |
| **없어도 돈다** | Ollama 가 죽었거나 응답을 못 알아들으면 카탈로그 앞 다섯으로 물러선다. 그 다섯은 원전 1절 기법표 넷 + 4절 첫 항목이라 임의로 고른 것이 아니다 |
| **질의가 없으면 안 부른다** | `/saved` 처럼 질의가 없는 자리에서는 고를 근거가 없다. 근거 없이 부르면 비용만 쓰고 답을 지어낸다 |

## 그래서 코드가 이렇게 된다

| 파일 | 무엇 |
|---|---|
| `src/structure.js` | **신규.** `parseSelection` · `fallbackSelection` · `selectStructures` |
| `server.js` | `/api/expand` 가 `q` 를 받고 `selection` 을 함께 준다 |
| `public/app.js` | 질의를 보내고, 고른 다섯을 먼저 그리고 나머지 셋은 접어 둔다 |
| `public/app.css` | `.expand__more*` · `.expand__note-text` |
| `scripts/check-stage14.mjs` | **신규.** S14-G1~G9 |

### 여덟을 다 내려보내고 selection 으로 따로 말한다

다섯만 내려보내면 LLM 이 실패했을 때 화면이 그 사실을 모른 채 다섯만 그리고, 서버가 이미 계산해 둔
나머지 셋을 버리는 셈이 된다. 파생은 결정적이라(S11-G3) 여덟을 다 주는 비용이 사실상 없다.
화면은 고른 다섯을 그리고 나머지는 **지우지 않고 접어 둔다** — 고른 다섯이 마음에 안 들 때 볼 자리가 있어야 한다.

### 무엇이 골랐는지 화면이 밝힌다

`LLM 이 고름` / `기본 순서` 배지를 단다. 안 적으면 **Ollama 가 죽어 있어도 화면은 똑같이 다섯 장**이라
사용자는 늘 자기 질문에 맞춰 뽑힌 것이라고 믿게 된다.

### 모델 출력은 신뢰하지 않는다

`parseSelection` 이 카탈로그에 없는 id·중복·개수 이상을 전부 걸러 낸다. 모자라면 카탈로그 순서로
채운다 — 다섯을 못 채웠다고 통째로 버리면 모델이 셋만 맞혀도 그 판단까지 잃는다.
`parseRewrite` 가 의도만 나와도 살리는 것과 같은 선택이다.

## 선택 품질은 게이트로 못 박지 않았다 (실측만 남긴다)

모델 출력은 흔들리므로 게이트로 박으면 통과 여부가 모델 버전에 좌우된다. 대신 **원전이 스스로 말한
대응**(진단표 → 구조)을 기준으로 재서 기록만 남긴다. 8건, 같은 씨앗으로 두 번 돌려 결과가 같았다.

| 프롬프트 | 1위 | 다섯 안 | 평균 지연 |
|---|---|---|---|
| `principle` 만 | 5/8 | 7/8 | 484ms |
| `principle` + `detail` | **7/8** | **8/8** | 407ms |

**빠진 것의 원인이 프롬프트에 있었다.** `평면적이고 깊이가 없어 보여요` 에서 `공기원근` 이 통째로
빠졌는데, 그 구조의 `principle` 은 기법만 말하고(`먼 쪽은 대비·채도를 낮추고…`) **증상 낱말이 없다.**
`평면`·`깊이` 는 `detail` 에만 있고 프롬프트는 `principle` 만 보내고 있었다.

### 그런데 그 수정이 처음엔 아무 일도 하지 않았다

프롬프트가 `detail` 을 쓰도록 고쳐 놓고, **`server.js` 가 카탈로그를 만들 때 그 필드를 떨어뜨리고
있었다.**

```js
const structureCatalog = loadStructures().map((x) => ({ id: x.id, name: x.name, principle: x.principle }));
//                                                                                  detail 이 없다
```

프롬프트의 `detail` 자리가 늘 빈 문자열이라 개선이 통째로 무효였다. **A/B 실험은 프롬프트를 직접
조립해서 좋아진 것이고, 제품은 안 고쳐진 상태였다.** 재측정에서 같은 케이스가 그대로 빠져 발견했다.

이 저장소가 이미 기록한 것과 같은 부류다 — `warmUp` 이 import 만 되고 호출부가 없었는데 "워밍업으로
빨라졌다" 고 보고한 일(`2026-09-01-session-summary.md`). **필드를 넣는 것과 그 필드가 실제로 쓰이는
것은 다르다.**

`S14-G9` 를 신설했다. 코드 모양이 아니라 **완성된 프롬프트 문자열**에 각 구조의 `principle` 과
`detail` 이 들어 있는지 보고, `server.js` 의 카탈로그 조립부가 네 필드를 다 넘기는지 함께 본다.
음성 대조로 "detail 을 뺀 카탈로그로 만들면 `평면적` 이 사라진다" 도 확인한다.

## 리뷰 (격리 worktree 둘, 라운드 9)

`typescript-reviewer` **LOW 2 · Approve**, `code-reviewer` **HIGH 2 · MEDIUM 1**. 전부 반영했다.

### [HIGH] 게이트가 기대값을 검사 대상 자신에게 물었다

`S14-G2` 가 "폴백 = 카탈로그 앞 다섯" 을 검증한다면서 기대값을 `fallbackSelection()` 으로 만들었다.
그러면 그 함수가 무엇을 내든 기대값도 같이 따라간다 — **폴백 순서를 통째로 뒤집어도 G1·G2 가 둘 다
통과했다**(재현 확인). 기대값을 `data/structures.json` 에서 직접 읽도록 고쳤다.

이번 세션에서 **세 번째**로 만든 "통과하지만 아무것도 안 잡는 게이트" 다(S13-G6 의 첫 판,
S13-G7 의 슬라이더 범위 검사, 그리고 이것). 셋 다 뮤테이션이 아니었으면 못 찾았다.

### [HIGH] 배지가 거짓말을 하고 있었다

모델이 카탈로그에 없는 id 만 줘도 `from: "llm"`, `error: null` 이었다. 결과는 카탈로그 앞 다섯과
**바이트 단위로 같은데** 화면은 "질문에 맞는 5가지를 로컬 LLM 이 골랐습니다" 라고 말했다.
**배지를 단 이유가 바로 그 구분이었는데 그 배지가 틀린 값을 읽고 있었다.**

`parseSelection` 이 `{ ids, matched }` 를 돌려주게 하고, `matched === 0` 이면 `from: "fallback"` 에
이유를 붙인다. 부분적으로 맞히면(예: 다섯 중 둘) 화면이 "둘을 골랐고 나머지 셋은 기본 순서로
채웠습니다" 라고 말한다. `S14-G8` 이 실제 서버를 세워 이것을 검사한다 — 정적 검사로는 못 잡는다.

### [LOW] 개수 축에 방어가 없었다

"모델 출력은 신뢰하지 않는다" 를 `id` 축에는 적용하면서 `count`·`validIds` 축에는 안 했다.
`count` 가 NaN 이면 카탈로그를 통째로 돌려주고 음수면 빈 배열이 됐다. 지금은 닿지 않지만
export 된 함수라 조였다 — `usableCount` 가 채울 수 있는 만큼으로 자른다.

### [LOW] `.expand__note` 가 두 곳에 정의돼 있었다

지금은 속성이 안 겹쳐 결과가 같지만, 겹치는 속성을 더하면 소스 순서에 좌우되는 버그가 된다. 합쳤다.
