# 2026-09-07 — `/saved` 가 저장된 재질을 보여준다 (22단계)

## 무엇이 안 됐나

파생 팔레트를 저장하면 재질이 남고(19단계), 엔진 수치로도 나가는데(20단계), 정작
**목록에서는 안 보였다.**

```
전:  보색대비  [어두운 배경]                 ← 재질이 어디에도 없다
     ▬▬▬▬ 40%  ▬▬ 30%  ▬▬ 30%
```

사용자가 자기가 무엇을 저장했는지 알려면 **내보내기를 눌러 JSON 을 읽어야 했다.**
21단계가 재질을 고를 수 있게 만들면서 이 구멍이 더 커졌다 — 고르고 저장했는데
확인할 자리가 없다.

후:  보색대비  [어두운 배경]
     ▬▬▬▬ 40%  ▬▬ 30%  ▬▬ 30%

## 정한 것 셋

### 1. 한글 이름은 서버가 준다

저장에는 **id 만** 남는다(`matte`). 화면에 그대로 찍으면 사용자가 무엇인지 모른다.

화면에 한글 이름을 박으면 `data/finishes.json` 을 고쳐도 **안 따라오고, 그 어긋남은
아무도 안 알려 준다.** `/api/expand` 가 같은 이유로 이미 같은 표를 보내고 있어서(17-B),
그것을 `/api/saved` 에도 싣는다 — `limits` 를 싣는 것과 같은 자리라 요청을 더 만들지 않는다.

표를 만드는 곳도 한 군데로 모았다(`FINISH_NAMES()`). 두 곳이 같은 표를 따로 적으면
한쪽만 고쳐질 자리가 생긴다.

### 2. 누가 골랐는지 밝힌다

`finishesAdjusted` 면 `[직접 고른 재질 있음]` 이 붙는다. **문구는 리뷰 뒤에 바뀌었다** —
처음엔 `직접 고름` 이었는데 아는 것보다 많이 말했다(아래 Medium① 참조).

**비율에는 안 붙인다.** 비율은 **그 화면에서 바로 고칠 수 있어서** 출처가 덜 중요하다 —
마음에 안 들면 그 자리에서 슬라이더를 움직이면 된다. 재질은 여기서 못 고치므로
"왜 이게 메탈릭이지" 를 답해 줘야 한다.

### 3. 손상된 값은 색과 같은 규율로 거른다

모르는 재질 · 이 구조에 없는 역할 · 타입 위장 · 프로토타입 키를 버린다.
**거부가 아니라 걸러내기다** — 하나 틀렸다고 항목을 통째로 안 보여주면 사용자는
멀쩡한 색과 비율까지 잃는다.

18-B 에서 `savedCard` 가 `entry.colors` 를 가드 없이 읽어 **항목 하나가 목록 전체를
비운** 적이 있다(리뷰 High). 재질을 새로 그리면서 그 자리가 다시 생긴다.

## 뮤테이션이 두 번 설계를 바꿨다

변형 19개를 돌렸고, 처음에 **여섯이 살아남았다.** 그중 넷이 화면 쪽이었다.

### ① 정적 검사가 동작을 안 봤다 (넷)

`saved.js` 소스에서 `fields.finishes` 라는 **글자를 찾는** 방식이었다. 그러면
`if (false)` 로 감싸거나 `void` 로 버려도 통과한다.

**21단계 `S21-G4` 와 정확히 같은 부류이고 처방도 같다** — 그리는 부분을 `finishLine`
이라는 순수 함수로 빼고 게이트가 직접 부른다. 넷 중 셋이 그것으로 잡혔다.

### ② 남은 하나는 게이트가 아니라 설계로 없앴다

이름표를 모듈 전역 `let finishNames` 에 두었더니 **"목록을 받을 때 채운다" 는 순서에
기대게** 됐다. 채우는 줄을 카드 그리는 줄 뒤로 옮기면 **첫 그리기가 id 를 그대로 보인다.**
게이트가 그 순서를 볼 방법이 없었다.

**인자로 넘기게 바꿨다. 그러면 틀릴 순서 자체가 없어진다.**

> 게이트를 하나 더 만드는 것보다, **틀릴 수 없게 만드는 것**이 낫다.

### 남은 둘은 등가 변형

`Object.hasOwn` 과 `Array.isArray` 검사를 지워도 안 잡힌다(리뷰가 독립적으로 재확인했다) —
프로토타입에서 나오는 것은 **함수·객체라 뒤의 `typeof id !== "string"` 에 걸리고**,
배열 표에는 한글 역할 키가 없어 조회가 늘 `undefined` 다.

그래도 두는 것은 **그 함수가 무엇을 읽는지가 계약**이기 때문이다 — 뒤의 검사가
언제까지나 지금 모양일 보장은 없다. 19단계 `pickFinishes` 와 같은 판정이다.

### 그리고 게이트 자신이 두 번 헐거웠다

- `savedCard(...finishNames...)` 를 찾는 검사가 **함수 선언**에 만족했다.
  호출부(`append(savedCard(`)로 좁혔다.
- 이름표를 받는지 보는 검사가 지역 변수 이름만 봐서, 응답에서 안 꺼내도 통과했다.
  `await api(` 에서 구조 분해하는 자리로 좁혔다.

**둘 다 "넓게 잡으면 미탐" 의 사례다.** 20·21단계에서는 반대로 넓게 잡아 거짓 실패를 냈다.
슬라이스·정규식 검사는 **양쪽을 다 확인해야 한다.**

최종적으로 **변형 19개 전부 잡힌다**(등가 2 제외). 리뷰 뒤 `S22-G6` 변형 8개도 전부 잡힌다.

## 격리 리뷰 두 건 — Critical 0 · High 0 · Medium 2 · Low 3

### Medium① — 배지가 아는 것보다 많이 말했다

`finishesAdjusted` 는 **항목 전체에 하나뿐인 참·거짓**이다 — 역할 셋 중 **하나라도** 기본값과
다르면 참이 된다. 그런데 문구가 `직접 고름` 이었고 줄 끝에 하나 붙으니 **셋 다 손으로
골랐다는 뜻으로 읽혔다.**

```
바탕 광택 · 본문 메탈릭 · 강조 발광  [직접 고름]
  ↑ 이것만 골랐는데      ↑ 이 둘은 기본값인데 같이 고른 것처럼 보인다
```

배지를 붙인 이유가 *"왜 이게 메탈릭이지" 를 답해 준다* 였는데, **안 고른 둘에 대해서는
거짓말을 하고 있었다.**

역할마다 표시하려면 기본 배정표가 화면에 있어야 하고, 그것은 `src/material.js` 에 있어
내리면 사본이 하나 더 생긴다. **아는 만큼만 말하는 쪽**을 골랐다 — `직접 고른 재질 있음`.
되돌릴 자리를 정확히 알려 주는 것은 홈 화면의 `(LLM 배정)` 표시가 이미 한다.

### Medium② — README 표가 세 단계째 낡아 있었다 (C3 가 실제로 터졌다)

게이트 수를 **세 곳**에서 맞춰야 하는데 나는 **두 곳만** 봤다. README 의 단계별 표에
S20·S21·S22 행이 없어서 합계 **156**, 선언 **175** 로 벌어져 있었다. 20단계부터 시작된
드리프트이고 **세 단계 연속** 놓쳤다.

이것이 작업 목록의 **C3** 다 — *"게이트 수 3곳 일치를 사람이 센다. 한 번 어긋난 적 있다."*
손으로 세는 동안 **또 어긋났다.**

**게이트로 만들었다(`S22-G6`).** 검사기를 하나씩 실제로 실행해 얻은 수가 기준이고, 문서
셋을 거기 맞춘다 — 문서끼리만 대조하면 넷이 사이좋게 틀릴 수 있다. **합계만이 아니라
단계별로도** 본다(합계만 보면 한 단계가 넘치고 다른 단계가 모자라도 통과한다).

**만들자마자 자기 자신을 잡았다** — 게이트가 176개가 됐는데 문서 셋이 175 였다.

> 잊지 말자고 적는 것과 잊을 수 없게 만드는 것은 다르다. **C3 이 닫혔다.**

### Low — 프로토타입 공격 케이스가 헛돌았다. 두 번째다

TS 리뷰가 `S22-G2` 의 `{ __proto__: "matte" }` 를 짚었다. 객체 리터럴에서 그것은
**공격이 아니다** — 값이 객체가 아니라 프로토타입 대입이 조용히 무시되고, own 속성도
상속 속성도 안 생긴다. 그 케이스는 `Object.hasOwn` 이 있든 없든 **똑같이 통과한다.**

```
{ 바탕:"matte", __proto__:"matte" }        → own 속성인가: false · 키 목록: ["바탕"]
JSON.parse('{"__proto__":"metal"}')        → own 속성인가: true  · 값: "metal"
```

**19단계에서 정확히 같은 지적을 받고 `postRaw` 로 고쳤는데 또 했다.** 리터럴로 쓴
프로토타입 케이스가 이 저장소에서 두 번 헛돌았다. 원문 JSON 세 가지로 바꿨다.

**바꾼 뒤에도 두 방어(`Object.hasOwn`·`Array.isArray`)는 등가로 남는다 — 이제 진짜 공격
형태로 확인한 등가다.** own 속성이 되어도 그 이름이 이 구조의 역할 목록에 없어 반복문이
묻지도 않고, 물었더라도 뒤의 `typeof`+목록 검사가 같은 결과를 낸다. 리뷰와 게이트 양쪽에서
확인했다.

### Low — 정적 검사가 평범한 리팩터링을 거부한다

TS 리뷰가 `S22-G3` 의 정적 부분을 네 가지 리팩터링으로 시험했고 **전부 거짓 실패**였다
(거짓 통과가 아니라). 그중 하나(널 가드를 빼고 인라인)는 **실제로 버그**다 — 코퍼스 카드에서
`finishLine` 이 `null` 을 돌려주는데 진짜 DOM 은 그것을 `"null"` 이라는 글자로 붙인다.

**안전한 방향의 마찰이라 두기로 했다.** 게이트가 울면 사람이 판단한다. 반대 방향(거짓 통과)
이었으면 고쳤다.

### Low — 손상된 저장에 역할이 중복되면 줄도 중복된다

`colors` 에 `바탕` 이 둘 있으면 재질 줄도 둘 나온다. 안 던지고 `undefined` 도 안 새므로
`S22-G5` 의 보장은 지킨다. **거부가 아니라 걸러내기** 원칙과도 맞아 그대로 둔다.

### 문제없다고 확인된 것

- **DOM 흉내 추출에서 잃은 것 없음.** 21단계 게이트 일곱 전부 통과, 뽑아낸 블록이 원본과 동일.
- `append` 가 숫자·`null` 을 글자로 안 바꾸는 차이는 있지만 **안전한 방향**이다(그런 값이
  들어오면 조용히 통과하는 게 아니라 터진다). 22단계의 호출부는 전부 문자열·노드만 넘긴다.
- 재질 순서·코퍼스 경계·이름표 부재 시 물러섬 — 전부 설계대로.
- `FINISH_NAMES()` 가 한 곳으로 모여 두 API 가 같은 표를 쓴다.

**A 묶음에 A4 하나만 남았다. 시작 전에 결정이 필요하다.**

`public/app.js` 가 이렇게 적어 뒀다:

> 카드마다 다른 모드로 나란히 비교할 수 있고, 이 저장소에 없던 저장 계층을 들이지도 않는다.

합치는 길은 있다 — **기본 모드만 저장하고 카드별 어긋남은 그대로 두는 것.** 새로 펼치는
카드는 저장된 모드로 시작하고, 그 뒤 카드마다 따로 토글할 수 있다. 그러면 "나란히 비교" 도
살고 새로고침도 견딘다.

**다만 저장 계층(localStorage)을 들이는 것은 그대로다.** 이 저장소가 지금까지 피해 온 것이고,
한번 들이면 다음 것(비율? 재질? 마지막 질의?)도 거기 들어가기 쉬워진다.
