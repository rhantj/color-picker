## 왜 그렇게 했나

- **입력 헥스를 코퍼스 색으로 바꾸지 않는다.** 34단계는 "빨간" 을 코퍼스 최근접으로 보냈지만, 헥스는 사용자가 이미 정한
  색이라 그대로 씨앗으로 쓴다. 구조 8가지의 강조(`accent-by-chroma`·`warm-neutral`)에 입력 헥스가 그대로 앉는 것을 S35-G3 이 잰다.
  코퍼스 밖 헥스라는 사실은 숨기지 않고 "가장 가까운 코퍼스 색 코럴 #F48067" 로 옆에 적는다 — 짝은 그 색으로 찾았기 때문이다.
- **합성 씨앗 = 입력 색 두 자리.** `expandSeed` 는 2색 씨앗을 받는다. 한 자리를 회색으로 두면 `accent-by-chroma`·`warm-neutral`
  이 회색을 바탕으로 잡아 입력 색이 사라진다. 두 자리 모두 입력이면 `splitSeed` 가 어느 쪽을 골라도 같다.
- **코퍼스 이름이 낱말보다 앞.** "빨강" 은 코퍼스에 그 이름의 색(#CC1236)이 실제로 있다. 낱말 최근접으로 보내면 다른 색이
  나온다 `[실측]`. 검사기의 낱말 픽스처를 "붉은·파란·잿빛·초록색" 으로 바꾼 이유다.
- **거리 함수 `[판단]`** — 지각 채도 평면(c·cos h, c·sin h)과 명도 l 의 유클리드 거리. 회색은 c≈0 이라 색상각이 자연히 무시된다.
  원전은 "가까운 색" 을 정의하지 않는다. 명도를 빼면 검정·흰색이 한 점이 된다 — 음성 대조로 확인.
- **LLM 이 다섯을 고르지 않는다.** 헥스에는 인상(질의)이 없어 고를 근거가 없다. 8장을 카탈로그 순서로 전부 보인다.
- **저장 없음(F1).** 파생 저장은 씨앗 id 로 서버가 색을 재계산한다(`store.js` 규칙 4). 사용자 헥스는 씨앗이 아니라 새 경로가
  필요하다 — 이 단계에 안 넣고 `open-work.md` F1 로 남겼다.
- **버린 대안**: (a) 짝 대신 입력 색을 코퍼스 최근접으로 스냅해 `/api/expand` 재사용 — 사용자 색이 사라진다. (b) 짝을 LLM 에 묻기 —
  근거 없이 색이 매번 달라진다. (c) 짝 카드에 `paletteCard` 재사용 — 풀 24쌍은 `type`·`hueRelation`·`score` 가 없어 못 그린다.
  `swatchView` 로 작은 카드를 새로 만들었다.
