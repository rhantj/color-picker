# 2026-09-06 — 씨앗 조합을 배색 구조로 불리기 (11단계 A: 색 파생 엔진)

[진단에서 조합으로(10단계)](2026-09-06-diagnosis-to-palette.md) 다음. **화면·API·LLM 은 이 단계에
없다.** 색을 만드는 순수 함수와 그것을 지키는 게이트 8개만 넣었다.

## 무엇을 하려던 것인가

사용자 요청은 "LLM 이 RAG 의 색 조합을 기반으로 여러 가지 색 조합을 보여주게 하고, 가장 많이
쓰는 5개를 뽑아서 화면에 보여준다" 였다. 두 가지를 먼저 확정했다.

| 물은 것 | 고른 것 |
|---|---|
| "5개" 가 무엇의 5개인가 | 씨앗 한 쌍을 불린 배색 5가지 |
| 새 헥스를 누가 정하는가 | **코드가 HSL 로 계산. LLM 은 구조만 고른다** |

두 번째가 이 단계 전부를 규정한다. LLM 이 헥스를 지어내면 같은 질의가 매번 다른 색을 내고,
명도 대비를 게이트로 검사할 수가 없다.

## 왜 이것부터인가 — Ollama 는 이미 붙어 있었다

세션을 "올라마 LLM 연결" 로 시작했지만 **연결은 이미 되어 있었다.** 실측으로 확인했다.

| 확인 | 값 |
|---|---|
| Ollama | 0.33.3, `127.0.0.1:11434` 응답, `exaone3.5:7.8b` |
| `/api/status` | `stage: 2`, `state: "ready"` |
| 저신뢰 질의 실제 호출 | 2단계 승급 → `intent: "palette"`, 재작성 **382ms** |

그래서 "연결" 이 아니라 **LLM 에게 시킬 새 일** 이 없는 것이 문제였다. 지금 LLM 은 검색어만
다시 쓰고, 화면에 나가는 문장과 색은 전부 코퍼스 원문이다. 8개 구조를 만들어 두면 LLM 이
"이 질의에 무엇을 보일까" 를 고르는 실제 판단을 하게 된다 — 그게 11-B 다.

## 어떤 원리를 썼나 — 구조를 지어내지 않았다

배색사전 16쌍은 **전부 2색**이라 바탕·본문·강조가 있는 화면을 못 짠다. 그런데 "그럼 어떤 구조로
불릴까" 를 배색사전은 말하지 않는다. `color-design` 스킬(이미 진단 코퍼스의 출처)에서 가져왔고
항목마다 어느 절에서 왔는지 적었다.

| 구조 | 출처 |
|---|---|
| 톤온톤 · 톤인톤 · 보색대비 · 유사색대비 | 1절 기법표 |
| 명도 스케일 · 강조색 | 4절 웹·앱 UI 색 결정 |
| 따뜻한 뉴트럴 · 공기원근 | 진단표 |

**숫자는 데이터에 넣지 않았다.** 몇 도 벌리고 채도를 몇 % 누르는지는 원전에 없다.
`data/structures.json` 에는 문자열만 들어가고 파생 규칙은 `src/expand.js` 한 곳에 있다 —
`public/ratio.js` 가 면적 규칙을 혼자 들고 있는 것과 같은 자리다. S11-G1 이 이걸 강제한다
(모든 필드가 문자열이어야 통과하므로 `hueShift: 180` 같은 필드가 생기면 바로 운다).

## 측정이 설계를 세 번 바꿨다

### 1. "보색" 이 180도가 아니었다

배색사전이 `보색` 이라 적은 **7쌍**의 실제 색상환 간격을 재 보니 **113.8~177.4도**였다.

```
pair-01 122.3   pair-02 146.3   pair-03 165.7   pair-04 176.5
pair-07 113.8   pair-10 177.4   pair-16 148.8
```

`보색에 가까움` 1쌍(pair-15, 158.9)을 더해 8쌍으로 봐도 범위는 같다.
(**처음 주석에 "9쌍" 이라고 적었다가 리뷰에서 잡혔다.** 세어 보지 않고 눈대중으로 적은 값이다.
이 저장소는 `[실측]` 을 근거로 인용하는 규율을 쓰므로, 틀린 실측치는 다음 사람을 잘못 인도한다.)

원래는 "씨앗이 이미 보색이면 그 관계를 그대로 살린다" 로 쓰려 했다. 그러면 `보색대비` 구조가
114도짜리 결과를 내면서 이름은 보색이라고 말하게 된다. **씨앗 관계를 이어받지 않고 정확히 180을
새로 여는 쪽**으로 바꿨고, `data/structures.json` 의 설명도 같은 자리에서 함께 고쳤다.

### 2. `#00ffee` — HSL 의 s 는 지각 채도가 아니다

옥색(`#00978D`, s=1.0)의 명도만 0.5로 올렸더니 형광 청록이 나왔다. 톤온톤의 설명이
"통일·안정, 차분한 깊이" 인데 정반대다.

눈에 보이는 쨍함은 `s` 가 아니라 **`C = (1-|2l-1|)·s`** 다. 명도가 0.5 에 가까울수록 같은 `s`
가 더 쨍해진다. `#00ffee` 는 `C = 1.00` 으로 가능한 최대치였다.

**명도 앵커마다 채도 상한**(`S_CAP`)을 달아 막았다. 다만 그 상한은 **역할에 맞춘 값이지 지각
채도를 고르게 맞춘 값이 아니다** — `light` 가 가장 낮은 것은 그 자리가 언제나 바탕이라 조용해야
하기 때문이고, `dark` 가 가장 느슨한 것은 명도가 이미 `C` 를 눌러 주기 때문이다. 그래서 값은
단조 증가하고, 지각 채도로 보면 `mid` 가 여전히 가장 높다(본문·강조는 색으로 읽혀야 하므로 의도한
것이다). **처음 주석에는 "중간 명도의 상한이 가장 낮다" 고 적혀 있었고 수치 배열과 정반대였다 —
리뷰가 잡았다.**

그리고 이 표만으로는 형광선을 못 지킨다는 것이 같은 리뷰에서 드러났다 — 아래 4번.

### 3. `따뜻한 뉴트럴` 이 따뜻하지 않았다

"씨앗과 무관한 색을 새로 만들지 않겠다" 며 회전량에 40도 상한을 뒀는데, 옥색(175)·라벤더(246)
씨앗에서 135도(연두)에 멎었다. 이름이 거짓말을 한다. 상한을 빼고 **난색 구간(15~55도)으로
밀어 넣는다.** 어느 씨앗을 쓸지만 씨앗이 정하고, 그 색상각이 이미 구간 안이면 그대로 둔다.

### 4. 톤인톤이 원전보다 쨍한 색을 만들고 있었다 (리뷰가 연 문)

리뷰가 지적한 것은 주석 하나였는데, 그 주석이 맞는지 재 보다가 실제 결함이 나왔다.

톤인톤은 두 씨앗의 `l` 과 `s` 를 **따로 평균**한다. 그러면 `l` 이 0.5 쪽으로 당겨지면서
`C = (1-|2l-1|)·s` 가 두 씨앗 어느 쪽보다도 커진다.

```
씨앗   로즈핑크 #DA525D C=0.533   민트그린 #00B49B C=0.706
파생   #db1525 · #8edb15 · #15dbbf   C=0.776   ← 씨앗 최대(0.706)도, 코퍼스 최대(0.729)도 넘는다
```

**배색사전 32색 어디에도 없는 강도의 색이다.** 평균 뒤에 씨앗 중 높은 쪽의 지각 채도까지 `s` 를
되돌리도록 고쳤다(`C=0.706`).

그리고 **주석으로 남기지 않고 게이트로 만들었다 — `S11-G9`.** 파생색의 지각 채도가 코퍼스 32색의
최대치를 넘지 않는지 본다. **상한을 숫자로 적지 않고 코퍼스에서 읽는다** — 적어 두면 구현을 고칠 때
게이트도 함께 느슨해진다. 뮤테이션으로 확인했더니 이 게이트 하나가 방금 고친 회귀(0.776)와 원래
사고였던 `#00ffee`(1.000) 를 **둘 다** 잡는다. 여덟 게이트 중 아무도 그걸 보고 있지 않았다.

## 함정 기록

- **`cat > file << 'EOF'` 로 200줄짜리 JS 를 쓰려다 셸이 통째로 깨졌다**(`unexpected EOF`).
  파일은 만들어지지도 않았다. `docs/troubleshootings/2026-09-01-tooling-traps.md` 1번이 말하는
  것과 같은 부류다 — **이스케이프·유니코드가 섞인 JS 는 셸로 쓰지 않고 Write 로 통째로 쓴다.**
- **`/tmp` 가 Node 에서 `D:\tmp` 로 해석된다**(Git Bash 셸과 Node 의 CWD 기준이 다르다).
  셸 heredoc 으로 만든 임시 파일을 Node 에 넘길 때는 절대 경로를 쓴다.
- **`while IFS= read` 가 마지막 줄을 흘린다.** 개행 없이 끝나는 파일에서 게이트 하나가 조용히
  안 돌았고, "75개 중 74개 통과" 로 보였다. 추출할 때 끝에 개행을 붙였다.
- **`review-fanout.sh` 의 `--round` 는 양의 정수만 받는다.** `11a` 같은 라벨은 거부된다.
  이 저장소는 라운드 1~5 가 이미 고정돼 있어 6을 썼다.

3. **화면** — 결과 카드에서 조합 하나를 펼치면 5장이 나온다. `public/ui.js` 의 `swatchView` 를
   3~4색에 맞춘다. 면적은 `ratio.js` 가 2색만 알므로 **3색 이상의 비율을 어떻게 할지 정해야 한다** —
   지금은 균등 분할로 물러서게 돼 있고, 그건 이 저장소가 "비율 없는 5:5 칩은 거짓말" 이라고
   적어 둔 것과 정면으로 부딪힌다. **11-B 를 시작하기 전에 이 결정부터 한다.**
4. 게이트 S11-G9~ 로 이어 붙인다 — LLM 이 5개를 고르는가 · 없는 구조를 지어내지 않는가 ·
   Ollama 가 죽어도 화면이 도는가.

## 열려 있는 것

- **3색 이상의 면적 비율 규칙이 없다.** 위 3번. `public/ratio.js` 는 2색이 아니면 균등 분할로
  물러선다.
- `따뜻한 뉴트럴` 이 씨앗을 거의 안 탄다(위 표). 의도한 것이지만 화면에서 여덟을 나란히 놓으면
  이것만 눈에 띄게 밋밋할 수 있다. 실제로 그려 보고 판단한다.
- `S11-G6` 의 색상 허용치 10도는 8비트 반올림 흔들림(실측 5.56도)의 약 2배다. 여유가 크지
  않으므로 게이트가 통과할 때도 실측값을 찍게 해 뒀다.
