# RAG는 생각보다 단순하다

- 출처: [GeekNews #32916](https://news.hada.io/topic?id=32916)
- 원문: [RAG is simpler than you think - Lighthouse Newsletter](https://www.lighthousenewsletter.com/p/rag-is-simpler-than-you-think)
- 정리일: 2026-09-01

## 핵심 주장

대부분의 RAG는 **BM25(전문 검색) + LLM 질의 재작성**이면 충분하다. 벡터DB와 임베딩부터 시작하는 것은 대개 과잉 설계다. 단순한 구조에서 시작하고, **실측 데이터가 복잡도를 요구할 때만** 단계를 올린다.

## 6단계 검색 구조

| 단계 | 구조 | 언제 쓰나 | 비용 / 지연 |
|---|---|---|---|
| 1 | 전문 검색만 (BM25 / Elasticsearch) | 키워드 중심, 정확한 용어 매칭 | API 비용 0, 10ms 미만 |
| 2 | + 에이전트 질의 재작성 | 회화체 질문, 어휘 불일치, 도메인 전문 용어 | 쿼리당 약 $0.001 |
| 3 | 하이브리드 (BM25로 50~100개 추출 → 임베딩 재순위 10개) | 의미론적 질문, 1~2단계로 부족할 때 | 월 약 $15 (일 1,000 쿼리), 200~500ms |
| 4 | 온디맨드 임베딩 | 문서 변동률 일 10% 이상 (뉴스·SNS) | 지연 높음, 임베딩 비용 지속 |
| 5 | 핫/콜드 계층 사전 임베딩 | 파레토 접근 패턴 (상위 20% 문서가 트래픽 80%) | 모델 교체 시 코퍼스 20%만 재임베딩 |
| 6 | 전체 사전 임베딩 | 일 10,000+ 쿼리, 안정적 코퍼스(월 5% 미만 변동) | 50ms 미만, 재임베딩 시 $10,000+ |

## 왜 1~2단계로 충분한가

- 청킹 전략 자체가 필요 없어짐
- 임베딩 모델 deprecation 리스크 없음
- 도메인 전문 용어는 오히려 키워드 검색이 강함
- 재임베딩이 없으므로 반복 개선 속도가 빠름

## 다중 의도 질의 처리

"CSV 읽고, 정제하고, 그래프 그려라"처럼 의도가 여러 개인 질문은 부질의(sub-query)로 쪼개 병렬 처리하고, 각각을 최적 경로로 라우팅한다. 저자는 이 방식으로 비용 15배 감소와 품질 향상을 달성했다고 주장한다.

## 의사결정 분포

- **60%** — 전문 검색 + 질의 재작성에서 종료
- **25%** — 하이브리드(온디맨드 / 핫·콜드) 추가
- **10%** — 대규모 사전 임베딩
- **5%** — 맞춤형 솔루션

> 60% 문제에 5% 수준의 솔루션을 만들지 말 것

## 댓글 반응

- 대규모 RAG 운영 경험상 전문 검색은 과소평가, 임베딩은 과대평가되는 경향이 있다는 동의
- 검색 기능을 오히려 제거했더니 성능이 개선된 사례 공유
- "LLM이 쓴 글 같다"는 지적 (AI 생성 문체 패턴)

## 유의점

본문의 비용·지연 수치는 원문 저자의 주장이며 벤치마크 근거가 제시되지 않았다. 특히 "비용 15배 감소"는 측정 조건이 명시돼 있지 않아 그대로 인용하기에는 근거가 약하다.
